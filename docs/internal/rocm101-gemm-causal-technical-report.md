# ROCm 10.1 与 PyTorch 2.14 升级后的矩阵乘性能排查

## 这次排查发现了什么

一次 ROCm 10.1 和 PyTorch 2.14 升级后，矩阵乘的结果没错，耗时却变长了。我们在同一块 gfx1200 GPU 上，用相同输入和 STABLE_PEAK 策略对照新旧版本，重点追查了一个 FP16 矩阵乘和一个小型 FP32 复合矩阵乘案例。最后找到三个原因：**CPU 在反复设置和维护相同的配置；新版可用算法中缺少合适的小 tile；GPU 算完乘加之后，尾处理和边界写回又多做了工作。** 这解释了本文重点排查的案例，不能据此认定整个新版软件栈、所有矩阵乘都变慢了。

这些判断都做了对照验证。把固定配置的设置和恢复移到循环外，FP16 案例原有的 CPU 连续提交差距就基本消失了。对于小 FP32 案例，我们保留新版构建，先修边界写回，再缩小 tile，GPU 时间从 6.587 μs 降到 5.300 μs，随后降到 3.813 μs。两项 GPU 改动的收益有重叠，不能把各自相对原版的节省直接相加。CPU 和 GPU 这两组结果也来自不同案例、不同计时方式，不能合成一个端到端加速比。

修复该从哪里入手，已经比较清楚。单次调用剩下的一些差距、部分硬件内部机制，我们还没有解释清楚；实验里的改法也没有完成生产验收。这些未解决的问题会继续留在因果树中。

正文按排查思路展开，先讲三个主要原因。需要核对数据时，可以查附录：那里保留了完整实验、上游提交、22 条因果边，以及没有通过控制检查的实验记录。E1—E20 只是证据索引，阅读正文时不必记住这些编号。

## 一 先弄清时间花在哪里

我们当时在升级一套 GPU 性能评测系统：从 Python 3.12.3、PyTorch 2.11.0+rocm7.2，换到 Python 3.14.4、PyTorch 2.14.0+rocm10.1.0。新旧软件都跑在当前主机驱动上。因此，这次比较的是重建的新旧用户态软件环境，没有把整台机器恢复到升级前的历史状态。

测试包括 FP16 矩阵乘 `A @ B` 和 FP32 复合矩阵乘 `A @ (B + B)`。文中的 M×N×K 表示 A[M,K] 与 B[K,N] 相乘，输出为 M×N。案例尺寸默认按原始行主序运算列出；后面用原生列主序接口做的补充实验，会单独注明。

这两种运算都经过 `torch.compile`。调用时，外层 Python 代码先检查条件、维护状态，再进入生成的执行程序，由它调用 GPU 内核或数学库。后文说的“调用包装”就是这层 Python 代码。所有正式性能比较都使用 STABLE_PEAK，硬件计数另行采集，避免把分析工具增加的耗时算进去。

我们先换了几种计时方式。CPU 向 GPU 提交任务后，不必等它完成，就能继续提交下一个任务。这意味着，在一次 Python 调用前后放两个 GPU 计时标记（event），量到的可能不只是 GPU 计算时间，还包括 GPU 等 CPU 提交后续工作的空隙。把多次调用录成执行图（graph）再重放，可以大幅减少逐次 Python 提交的影响。我们因此同时记录单调用 event、图中平均 GPU 时间和 CPU 连续提交时间。 [PyTorch 异步执行说明](https://docs.pytorch.org/docs/2.14/notes/cuda.html)

换一种测法后，两类问题开始分开。FP16 单次调用慢了 4.1%—9.9%，放进执行图后，差距缩到约 0.7%—1.5%。小 FP32 却仍然明显变慢：即使提前算好加法，只在图里测矩阵乘，16×16×32 案例的新耗时还是旧版的 2.091 倍。

我们也检查了生成程序，没有发现它多出计算步骤；新版新增的对齐复制路径，这些输入也没有触发。接下来便分两路查：FP16 重点看 CPU 调用包装，小 FP32 重点看 GPU 数学库。

不过，执行图还会改变队列、缓存和调度状态，图中平均耗时也不等于一次完整请求的延迟。到这一步，我们只是找到了继续排查的方向，还不能断言差距全在 CPU 或 GPU。具体原因，要靠后面逐项改动代码、替换组件来验证。

## 二 CPU 每次调用都在重复处理配置

CPU 分析工具先给出了一条线索：新版执行 2000 次编译后调用，记录到 16000 次上下文变量写入。顺着源码看，外层代码每次都要设置配置、恢复配置，还要记录“配置是否变过”。虽然每次调用请求的两个配置值相同，这些操作仍然照做。反倒是最先怀疑的输入检查，单独绕过后并没有消除新旧差距。

那么，如果把这两项固定配置的设置和恢复移到整个测量循环外，会怎样？我们保留配置值、输入检查和 GPU 代码，只移动这些操作。359×211×127 的 FP16 案例测得如下结果：

| 调用方式 | 旧版 μs/次 | 新版 μs/次 |
| --- | ---: | ---: |
| 原始调用 | 16.55 | 18.40 |
| 不变配置移到循环外 | 15.86 | 15.83 |

原先约 1.85 μs 的 CPU 提交差距基本消失了。我们随后固定新版，分别去掉配置值写入、字典变化状态维护和哈希失效标记，每项都测到了可重复的节省。另行跟踪调用时，没有发现哈希重算或字典重建。时间花在了反复写状态、调用维护函数上，即使有些函数读完状态就返回，也并非没有成本。

因此，对这个案例来说，重复处理配置是 CPU 提交变慢的主要原因。优化时应减少每次调用的重复工作，但配置隔离、异常恢复和并发行为都必须保留。实验中直接删掉维护代码，是为了查原因，不能照搬进生产。各项操作的对照数据见附录 B。

## 三 小矩阵找不到合适的小 tile

小 FP32 的问题更接近 GPU 端。我们写了一个直接调用 hipBLASLt 的 C++ 程序，让它绕过 Python 和编译框架，再交叉搭配新旧数学库与运行时。对 16×16×32 案例，耗时主要跟着数学库及算法资源变化；固定库、只换运行时，变化约为 0.05 μs。

接下来要分清：是好算法还在，只是没有选中，还是新版根本没提供？在本例的硬件、数据类型和布局下，旧版可用算法包含 8×8、16×16 的 tile，新版最小的却是 32×64。tile 是一个线程块负责计算的输出区域；矩阵很小时，分配更大的块，未必算得更快。我们把新版合法候选逐个测过，即使手动指定最快的那个，也追不上旧版。只调整已有候选的排序，解决不了这个案例的问题。

为了单独验证 tile 的影响，我们保留同一新版构建，先修好下一节要讲的边界写回，再只改每个线程负责的数据块大小，把整个 tile 从 32×64×16 缩到 16×32×16。这里前两维是输出块的大小，第三维是每步沿 K 方向处理的长度，并不是输入的完整 K。

GPU 时间从 5.300 μs 降到 3.813 μs，同轮配对节省 1.487 μs。另一种做法也有效：把旧小 tile 的整套配置接入新版。后文把这种连同线程组织、预取和访存设置一起使用的配置组合称为“配方”。

这说明，对这个案例，不必换回整套旧库，补入合适的小 tile 就能提速。不过，tile 变小后，计算量、寄存器、共享内存用量和边界分支也会跟着变。我们验证的是这项配置改动有效，还没有把收益逐一分给这些变化。候选枚举见附录 C，新版重建实验见附录 E。

## 四 乘加算完后又多做了哪些工作

小 tile 缺失只能解释一部分。我们特意选了新旧版本中 tile 相同的内核，新版还是更慢。反汇编和单独采集的硬件计数，把注意力引到了矩阵乘结束之后：尾处理和边界写回。

矩阵乘累加完成后，内核还可能要做缩放、加偏置或激活，再把结果写回。这部分通常叫尾处理。通用尾处理要支持多种功能，即使本次没用到偏置、激活，也可能先做一些准备工作。

写回方式也有区别：标量写回一次写一个元素，向量写回则在对齐允许时一次写多个元素。切换写回方式，变化的不只是写指令，还包括地址计算和等待安排。

我们从同一个新版内核出发，做了四组对照：尾处理保留或跳过，写回采用标量或向量。结果是，两项改动都能提速，但收益会互相影响。保留尾处理时，改成向量写回省得更多；两种尾处理条件下，写回优化的收益相差 0.682 μs，这就是时间上的交互项。

指令计数也出现了对应变化：四组对照算出的交互项是 97 条向量算术指令，集中在共享内存地址计算上。不过，其他指令和等待也同时变化，所以不能把这 0.682 μs 全算在那 97 条指令头上。

两处一起改后，这批新版内核从 6.581 μs 降到 4.489 μs，已经接近同期旧版的 4.451 μs。这里新旧都指定 32×64×16 tile，旧版最快的小 tile 是另一个参照，不能混用。这个结果说明，两条路径确实拖慢了本例；但耗时接近，还不能说已证明性能等价。四组数据和指令证据见附录 C。

### 不跳过尾处理还能提速吗

跳过尾处理可以帮助定位，却不能作为通用修复。真正修代码时，还得保留完整功能。我们因此固定新版源码、编译器、库和运行时，**保留通用尾处理**，只修普通边界路径的写回宽度：对齐条件允许一次写四个元素时，就不再退回逐元素写回。

这次重建后，大 tile 从 6.587 μs 降到 5.300 μs，再缩小 tile，降到 3.813 μs。图 3 把修复前后的两条线放在一起，能看到收益为什么重叠：这个尺寸已经填满小 tile 的 M 方向，不再进入原来的 M 边界分支。

为了核对这一点，我们把原生列主序接口里的 M 改成 12，N=16、K=32 保持不变，让小 tile 也碰到 M 边界。此时再修写回，又能省下 0.351 μs。这里的 M 是原生接口坐标，不能直接当作前文行主序输入的 M。

也就是说，修边界写回和补小 tile 都有效，而且不需要跳过通用尾处理。但两者会解决一部分相同的问题，应当一起评估，不能把它们各自相对原版的收益直接相加。这批数据来自源码重建，与前面的二进制改动分别统计。布局控制、正确性检查和配对结果详见附录 E。

**图 3｜边界修复和缩小 tile 的收益取决于输入边界。** 左图是原生列主序 M×N×K=16×16×32 的六轮对照，右图是 12×16×32 的另四轮对照。小点为各进程中位数，大点为它们的中位数，灰线是同时改变多个配置的旧配方。所有组合均保留通用尾处理；不同批次分别统计。[E13]

## 五 这些代价是作者有意接受的吗

我们把已测到的代码变化追溯到了五个上游提交。但找到改动的目的，不等于知道作者是否预料到了这次退化。证据最明确的是配置隔离：公开评审曾报告约 5% 的运行时开销，作者回应后继续推进了改造。这能说明作者知道部分基准会变慢，不能说明本文案例的损失无法避免。

小 tile 缺失和普通边界写回变化，则更值得作为疑似非预期问题去检查。两项改动原本分别为了解决特定尺寸的问题、让写回宽度能够自适应。公开材料没有说明作者有意牺牲本文这类小矩阵，也无法据此判断他们还做过哪些未公开的测试。缓存维护和通用尾处理同样有各自的功能目标，但作者是否预料到反复调用时的成本，目前证据不足。具体判断和评审出处放在附录 D。

### 剩下的问题还值得追到哪里

主因找到后，还有三个问题需要核对：

| 追查的问题 | 已经得到的结果 | 仍需保留的边界 |
| --- | --- | --- |
| 相同机器码为何有不同耗时？ | 只改变代码入口布局，就能复现时间变化；源码修复比较因此统一了入口偏移 | 尚未证明布局导致原始升级退化，也不知道具体取指或缓存机制 |
| 配置外移等诊断干预后，单调用 event 为什么还有差距？ | 预先排入 GPU 工作、移动计时边界，都能大幅缩小差距 | 观测钩子会扰动结果；无钩子对照也受波动限制，不能可靠分配各段原始成本 |
| 补回旧小 tile 后，配方还有多少优化空间？ | 单独开启局部预取有收益；保留其他代码、只收紧等待阈值，会抵消大部分收益 | 确认的是该条件下等待策略的作用，并非每条指令的周期数或任意配方的唯一分解 |

这些实验让我们更清楚哪些地方值得改，也让我们知道哪里该停。**只有新实验可能改变修复选择、收益判断，或者推翻主要结论，才值得继续追。** 对于已经小到难以和重复对照的波动区分的差值，我们不再硬拆；硬件内部每个周期发生了什么，也不作为这次排查的完成条件。各项残差、控制失败记录和重新启动排查的条件见附录 G。

下一步是把实验里的改法做成不破坏原有行为的修复，再验收：CPU 减少重复配置维护，GPU 修边界写回、补小 tile，还要确认默认算法选择能用上它们。新增的 64 项检查已经覆盖了一些 bias/ReLU 组合，但只验证了这些组合的正确性，没有测性能，也没覆盖完整功能、并发或所有尺寸。找到原因和交付修复，是两件事；验收要求见附录 H。

### 新旧版本采用相同策略并单独采集计数器

新旧版本都在 STABLE_PEAK 策略下测量。每次实验独占目标 GPU，开始前核验性能策略；无论正常结束还是异常退出，都恢复并核验 AUTO。AUTO 只用于实验后的恢复，不参与性能比较。

我们在计时区间之外记录了频率和温度。旧、新栈的 GPU 核心频率分别为 2736—2757 MHz 和 2735—2757 MHz，中位数都是 2747 MHz；显存频率都是 1258 MHz，热点温度中位数都是 70°C。两边的运行条件接近，但这些快照不能保证每一次内核执行时的瞬时频率完全相同。[E1]

性能计时期间不启用分析工具。硬件性能计数器（PMC）另行采集，用来观察内核执行了多少指令、使用了多少资源。分析工具本身会增加开销，所以它记录的时间不混入性能结果。

### 三种计时回答三个不同问题

| 计时方式 | 怎么测 | 测到什么 |
| --- | --- | --- |
| 单次调用的 event 时间 | 在一次调用前后放置 GPU 计时标记，最后等待完成 | GPU 执行时间，以及可能的任务提交空隙 |
| 执行图中的平均时间 | 将 100 次调用捕获成图，重复执行整张图，耗时除以 100 | 大幅减少逐次 Python 提交影响后的平均耗时 |
| CPU 连续提交时间 | 用 CPU 时钟测量连续提交 2000 次任务所用时间，计时结束后再等待 GPU 完成 | CPU 提交任务的成本，也可能包含运行时要求 CPU 等待的时间 |

执行图（graph）可以把一组 GPU 操作记录下来，之后整组重放，减少 Python 一次次发起调用的成本。我们还分别尝试提前初始化 event、推迟等待完成的时机，以及用一对 event 测量多次调用。需要注意，创建 Python event 对象不等于底层计时事件已经初始化，后者可能延迟到首次使用时才发生。[PyTorch Event 文档](https://docs.pytorch.org/docs/2.14/generated/torch.cuda.streams.Event.html)

主比较共运行四轮，每轮交替测试新旧栈的八个案例，每次都启动新进程，共 64 个进程。除另行说明外，耗时先取每个进程内样本的中位数，再取各进程中位数的中位数。新旧比值则先按轮配对计算，再取四轮比值的几何均值。同一进程中的重复计时用来观察波动，不算作来自不同机器的独立样本。

### 换一种测法后两类问题开始分开

下表用“新版耗时 ÷ 旧版耗时”表示变化，大于 1 即新版更慢。“编译后调用”经过 `torch.compile`；“只测 GEMM”提前准备输出缓冲区，并把加法移出计时部分。重点看差距在改变执行方式后是否保留，而不是将三列相减计算组件成本。

| 案例 | 编译后单次调用 | 编译后在图中执行 | 图中只测 GEMM |
| --- | ---: | ---: | ---: |
| G0 | 1.041 | 1.008 | 1.000 |
| G1 | 1.099 | 1.007 | 1.017 |
| G2 | 1.069 | 1.015 | 1.046 |
| G3 | 1.062 | 1.014 | 1.014 |
| C0 | 1.400 | 1.400 | 1.676 |
| C1 | 1.804 | 1.725 | 2.091 |
| C2 | 1.598 | 1.468 | 1.580 |
| C3 | 1.498 | 1.148 | 1.176 |

FP16 矩阵乘的结果首先指向 CPU 提交路径：单次调用慢了 4.1%—9.9%，放进执行图后只慢约 0.7%—1.5%。G2 的“只测 GEMM”平均比值为 1.046，但四轮结果从 0.996 到 1.129，波动较大，不能据此认定它稳定地慢了 4.6%。

FP32 复合矩阵乘则不同。即使减少 Python 提交影响，并把加法移出被测部分，GEMM 仍然明显变慢。C1 的耗时达到旧版的 2.091 倍，说明这里还有 GPU 端的问题。

检查全部 64 个生成的执行程序（runner）后，没有发现计算步骤增加：普通矩阵乘仍调用一次外部矩阵乘库，复合矩阵乘仍是一次 Triton 加法内核接一次外部矩阵乘。新版增加了地址对齐检查和必要时复制数据的逻辑，但所有测试输入都满足 16 字节对齐条件。至少从执行结构上看，不能用“新版多算了一步”解释回退；这还不等于两版 GPU 机器指令完全相同。[E1]

### 从观察到实验设计

我们据此安排了下面的实验：先分清计时中混进了哪些提交开销，再检查框架和数学库，最后改动具体代码路径。H5、H6 是看过候选算法和反汇编后才提出的，并非实验开始前就列好了所有猜想。

| 猜想 | 怎样检验 | 如果成立 应看到什么 |
| --- | --- | --- |
| H1 计时事件或任务提交空隙增加了耗时 | 改变事件初始化和等待方式，再用执行图减少逐次提交 | 新旧差距明显缩小 |
| H2 编译器让 GPU 多做了工作 | 检查生成代码、数据对齐和实际调用步骤 | 新版多了内核、数据复制或不同的计算拆分 |
| H3 HIP 运行时导致小矩阵变慢 | 固定数学库，只换运行时版本 | 耗时主要随运行时版本变化 |
| H4 输入检查或配置维护拖慢了 CPU 提交 | 分别绕过输入检查、移出重复配置操作 | 可以找到使差距缩小的具体操作 |
| H5 新版只是没有选中好算法 | 测量所有支持该输入的候选算法 | 新版仍有能接近旧版速度的算法 |
| H6 内核结束阶段做了额外工作 | 在同一内核中分别改变尾处理和结果写回路径 | 时间和执行指令数一起下降 |

到这里还只是找到线索。执行图减少了逐次 Python 提交的影响，CPU 和 GPU 究竟哪里慢了，还要分别往下查。

## 附录 B CPU 配置维护的干预证据

### 输入检查没有解释差距

PyTorch 在复用已编译代码前，会检查输入等条件是否仍符合编译时的假设，这些检查称为 guards。我们对四个 GEMM 案例分别做了绕过检查的实验，每个案例测试两轮，新旧差距仍然存在。因此，这些检查不是当前证据指向的主因。

CPU 分析工具给出了更具体的线索：新版执行 2000 次编译后调用时，出现了 16000 次 `ContextVar.set`，相当于每次调用八次。检查安装源码发现，`_make_closure_patcher` 会在每次调用前后设置和恢复配置，并标记配置哈希失效、维护配置字典的变化状态。标记失效并不等于当场重新计算哈希。旧版主要读写普通属性，新版则增加了上下文变量和状态维护。这些操作位于编译后函数的外层包装代码中。[E5]

### 把不变的配置移到循环外

验证方法是保留相同配置和 GPU 代码，只减少重复操作。`automatic_dynamic_shapes=False` 与 `assume_static_by_default=True` 的值保持不变，但它们的设置和恢复移到整个测量循环外，而不是每次调用都做一次。输入检查仍然保留。另一个对照实验进一步改变 fullgraph 模式的状态维护代码，用来观察这部分成本。

首轮实验中，代表案例 G1 在新旧环境各运行两个独立进程。每个进程进行 12 轮测量，以固定的随机顺序测试各条执行路径；每轮分别测量 2000 次连续任务提交和 200 次单调用 event 时间。所有执行路径都通过原有数值检查。[E5]

| 路径 | 旧主机提交 μs | 新主机提交 μs | 旧单调用 event μs | 新单调用 event μs |
| --- | ---: | ---: | ---: | ---: |
| 原始编译后调用 | 16.552 | 18.400 | 23.437 | 26.276 |
| 静态配置外移 | 15.856 | 15.827 | 22.847 | 24.342 |
| 再改变 fullgraph 状态维护 | 14.044 | 14.429 | 22.087 | 22.652 |
| 直接调用生成的执行程序 | 7.956 | 7.703 | 12.188 | 11.889 |

移走这些操作后，这一批新旧连续提交的汇总结果已不再显示原先约 1.85 μs 的差距。因此，我们把重复配置维护判断为 G1 提交变慢的主因。不过，这里没有按预设界限检验两者是否性能等价，而且一次移走了配置写入和状态更新，还分不清谁更贵。接下来固定新版，把这些操作逐项拆开测。

单调用 event 时间还剩约 1.50 μs 的差距；进一步改变 fullgraph 状态维护后，差距缩小到约 0.57 μs。这些是首轮特定条件下的差值，不能当作固定组件成本；附录 G E15 用排队对照进一步验证了外层包装、任务提交与 GPU 执行时序的影响。由于旧版也有 fullgraph 维护成本，不能把移除它节省的全部时间都算成新版新增的开销。

### 拆分配置值写入和状态维护

新的问题是：每次调用多花的时间，主要来自写入配置值，还是维护“配置变了”的状态？如果是后者，又是在反复重建缓存，还是只做了重复标记？

我们固定新版 Python/PyTorch、G1 输入、CPU 亲和性和编译代码，将两项静态配置放在共同的外层作用域。从实际安装的 `_make_closure_patcher` 源码生成诊断闭包，分别移除配置值写入、哈希失效标记和字典变化状态维护。各变体仍保留原值读取和循环骨架；“都移除”也不是空函数或完全删除 hook。每个编译函数均确认创建了对应闭包，输入检查保留，计时前后数值检查通过。[E10]

确认实验使用四个独立进程。每个闭包先预热两秒，每进程再做 12 轮随机顺序测量：纯闭包每项每轮执行 20000 次设置/恢复；真实任务每项每轮连续提交 2000 次，停止 CPU 计时后再同步。下表为四个进程中位数的中位数。这是新版内部的拆分实验，与上表首轮新旧比较分开统计。

| 保留的操作 | 纯配置闭包 μs | 真实任务提交 μs |
| --- | ---: | ---: |
| 原始代码 | 1.819 | 17.909 |
| 原始代码重复对照 | 1.818 | 17.866 |
| 只保留配置值写入 | 0.793 | 16.749 |
| 只保留两类状态维护 | 1.336 | 17.430 |
| 配置值写入和两类状态维护都移除 | 0.284 | 16.071 |
| 配置值写入与哈希失效标记 | 1.399 | 17.358 |
| 配置值写入与字典变化状态维护 | 1.270 | 17.216 |

按同一进程配对后取差值中位数，移除两类状态维护，真实提交节省 1.168 μs；移除配置值写入，节省 0.502 μs；两组都移除，节省 1.848 μs。单独移除字典状态维护和哈希失效标记分别节省 0.516 μs、0.684 μs。这些是不同条件下的效果，不能简单相加，也不能直接从上表汇总值相减得到。同期原始代码重复对照的提交差值范围为 −0.0196—0.1058 μs；纯闭包最大配对差约 0.0033 μs。

我们另用一个不参与性能计时的进程，跟踪原始闭包下的 200 次真实任务调用。记录到 1600 次 `ContextVar.set` 和 800 次 `_mark_get_dict_dirty`；后者全部读到 dirty keys 为 `None`，随后直接返回。该区间没有出现配置模块的 `get_hash` 或 `_get_dict` 调用。

G1 的 CPU 提交开销由此进一步缩小到两类工作：写入上下文状态，以及调用那些读完状态就返回的维护函数。在当前固定配置下，后者花的时间更多。图 B1 分别展示最初的新旧对照和后来固定新版的拆分结果，两批数据不合并。

## 附录 C GPU 库、候选与内核路径的干预证据

### 用原生程序验证 GPU 端的差距

针对 C1，我们编写了直接调用 hipBLASLt 的 C++ 测试程序，保留 16×16×32 的 FP32 矩阵乘，绕开 Python、Dynamo 和 Inductor。原生程序按列主序接口表示运算；与原始行主序运算对应时，转置表示会交换 M、N。C1 的 M=N，数值上看不出这项交换；后续非方形补充实验均明确使用原生接口坐标。最初用全部为 1 和全部为 2 的输入，检查输出是否全部精确等于 64；找到可疑算法后，再使用与主实验相同的固定随机输入验证。

测试程序把 100 次 GEMM 放进执行图，预热后测量整图重放时间，再除以 100。每个进程记录九个样本。这个结果代表连续重复执行时的平均耗时，不包含冷启动，也不等同于一次完整请求的延迟。

### 换库和换运行时分别测

接下来固定容器、测试程序、GPU 和主机驱动，交叉组合新旧数学库与新旧运行时。数学库这一组包含 hipBLASLt、依赖和算法资源；运行时这一组包含用户态 HIP/HSA 组件。每种组合运行四个独立进程，交替测试，并用 `ldd` 确认实际加载的是哪套库。[E2]

| 数学库及配套资源 | 旧运行时 μs | 新运行时 μs |
| --- | ---: | ---: |
| 旧库及算法资源 | 4.023 | 4.073 |
| 新库及算法资源 | 8.842 | 8.889 |

结果很清楚：同一套库只换运行时，耗时变化约 0.05 μs；换掉库和算法资源，变化却有数微秒。因此，对 C1 应当继续查 hipBLASLt 提供了哪些算法，以及它们生成了什么内核。

不过，这里替换的是一整组库和配套资源，暂时还不能把问题指定到某一个 `.so` 文件。新旧版本混用只是定位手段，不表示这种搭配受到支持或适合生产使用。

### 换一个算法能否解决问题

数学库通常会按启发式规则给候选算法排序。为了检查是不是“算法还在，只是没选好”，我们用 `getAllAlgos` 列出算法，再用 `matmulIsAlgoSupported` 检查它们是否支持当前矩阵尺寸、内存布局和临时工作空间限制。下面的算法 ID 只在对应库版本内有效，不能跨版本复用。[hipBLASLt 算法查询接口](https://rocmdocs.amd.com/projects/hipBLASLt/en/latest/reference/ext-reference.html)

对 C1，旧版有五个可用算法，其中包括 8×8 和 16×16 的计算块；新版只有四个，最小计算块为 32×64。这种计算块通常称为 tile，表示一个计算块负责处理多大的数据区域。也就是说，针对当前硬件、类型和布局，新版可选列表里已经没有旧版那些较小的 tile。

我们固定新版运行时，用相同的随机输入指定算法 ID，进行四轮比较：[E3]

| 库版本内算法 ID | tile | 耗时 μs |
| --- | --- | ---: |
| 旧 58749 | 16×16×16 | 4.082 |
| 新 85583 | 64×64×16 | 8.906 |
| 新 85585 | 32×64×16 | 6.593 |

切换到新版更快的候选，把 8.906 μs 降到了 6.593 μs，仍慢于旧版的 4.082 μs。因此，仅调整现有候选的排序不足以恢复性能。不过，这些算法还同时改变 tile、线程组织和尾处理，不能把全部差距直接归给 tile 尺寸。下面用相同 tile 的内核继续缩小范围。

实验中还发现，同一个排序位置在不同进程里可能对应不同算法。因此，后续计数器结果都按实际算法 ID 和内核名对应，而不是按“第几个候选”对应。早期按排序位置整理的结果不再用于结论。

### 各批 GPU 基线为什么不同

文中先后出现约 8.9 μs、6.6 μs 和 4 μs，是因为各批实验选的算法和参照不同，并非同一个算法一会儿快、一会儿慢。尤其要分清“旧版最快的小 tile”和“与新版 tile 相同的旧算法”，它们是两条不同的参照。

| 证据组 | 固定或改变什么 | 对应基线 μs |
| --- | --- | --- |
| E2 库与运行时替换 | 该批所选算法，替换整组库和资源 | 旧库 4.023—4.073；新库 8.842—8.889 |
| E3 指定算法 | 比较合法候选，找到新版更快的算法 | 旧小 tile 4.082；新 64×64 为 8.906，新 32×64 为 6.593 |
| E9 同 tile 四组干预 | 新旧均用 32×64×16，再改变新版两条路径 | 旧 4.451；新未干预 6.581 |
| E13 同一新版源码重建 | 保留尾处理，控制入口偏移，比较修复与候选 | 新原始 6.587；修写回 5.300；再缩 tile 3.813 |

各项收益都在本批对照中计算。这几行不能串起来，当成一次端到端优化逐步省下的时间。

### 先选相同 tile 再比内核

硬件计数器显示，新版内核执行了更多向量指令。不过，下面几项同时改变了 tile 大小、线程组织和资源用量，单凭这张表，还不能判断到底哪一项拖慢了计算。

| 固定算法 | VALU 每 dispatch | waves | wave size | VGPR | LDS bytes |
| --- | ---: | ---: | ---: | ---: | ---: |
| 旧 58749 | 239 | 1 | 64 | 32 | 4096 |
| 新 85583 | 5854 | 2 | 32 | 256 | 25088 |
| 新 85585 | 2874 | 1 | 32 | 168 | 14336 |

表中每项都采集三次，结果一致。dispatch 指一次内核启动；VALU 是按 wave 执行累计的向量算术逻辑指令数。wave 是共同执行指令的一组线程，其大小为 32 或 64，一个线程块可以包含一个或多个 wave。VGPR 是向量寄存器数量，LDS 是线程块共享的片上存储。VALU 不是浮点运算次数，尤其不能直接用 wave32 与 wave64 的计数比解释性能比。[E4]

为了减少这些差异，我们改用旧版算法 58759 与新版 85585 对照。两者的 tile 都是 32×64×16，均使用一个 wave32、168 个 VGPR 和 14336 字节 LDS。即便这些条件相同，新版仍然更慢，VALU 也从 2366 增到 2874。接下来需要检查它具体执行了哪些指令。

### 线索集中在计算结束后的处理和写回

查看实际加载的内核符号和反汇编后，差别集中到了矩阵乘结束阶段。旧版使用不带偏置的专用内核，新版则使用支持偏置（bias）、缩放（scale）和激活（activation）的通用内核。这些在乘加结果形成后、写回前后进行的操作，通常称为尾处理（epilogue）。

即使本例没有启用激活，新版仍会执行部分通用尾处理所需的地址计算、片上数据搬运和运算。写回方式也不同：输出第一维不足一个完整 tile 时，新版选择标量写回，而不是一次写入多个元素。但 C1 的这一维为 16，且满足对齐条件，可以使用一次处理四个元素、只写有效位置的方式。

由此可以做两个直接的尝试：在本例允许的条件下跳过通用尾处理，或者改成向量写回，看耗时是否下降。首轮先后改这两处，确认方向；后续再补齐四种组合，检查两项收益是否互相影响。

### 首轮验证 只改变两处分支

我们复制了一份新版内核二进制，只改变两处分支，其余字节保持不变。第一处让 alpha=1、beta=0、没有偏置和激活的本例，直接走已有的乘积写回路径；第二处让不足完整 tile 的边界也走已有四元素宽写回路径。实验使用临时容器挂载这份副本，没有替换系统库。

实验共四轮，每轮用四个独立进程交替测试四条路径。计时使用原来的固定随机输入；计时前后，都把全部输出与 CPU 双精度累加结果比较，绝对容差 atol 和相对容差 rtol 均为 1.25×10⁻⁵。容差与原测试相同，但参考结果由这个独立程序计算，而不是复用原框架的检查实现。[E6]

| 同 tile 路径 | 中位数 μs | 四进程中位数范围 μs | 独立 VALU 每 dispatch |
| --- | ---: | ---: | ---: |
| 旧版原始内核 | 4.468 | 4.451—4.493 | 2366 |
| 新版原始内核 | 6.593 | 6.587—6.595 | 2874 |
| 新版绕过通用尾处理 | 5.047 | 5.043—5.077 | 2544 |
| 再使用四元素宽掩码写回 | 4.508 | 4.486—4.526 | 2304 |

表中范围是四个进程各自中位数的最小值到最大值，不是置信区间。指令计数另用全 1、全 2 输入采集，每项三次结果一致；耗时则来自不启用分析工具的随机输入实验。

两处分支干预把同 tile 新旧差距从约 2.12 μs 缩小到 0.04 μs，证明这些路径确实影响当前案例的耗时。但第二步是在第一步已经修改后测得，不能将两步节省视为互不影响的固定成本。

修改后的 VALU 甚至低于旧版，因为直接写回还省掉了旧版执行的“乘以 alpha”；本例 alpha=1，这项运算不会改变结果。首轮最后约 0.9% 的耗时差没有继续归因。两者已经接近，但本实验没有进行统计检验来证明它们性能等价。

### 补齐四组对照看收益是否重叠

首轮先跳过通用尾处理，再改变写回方式，缺少“保留尾处理、只改写回”这一组。因此，还不能判断两项成本是否独立。后续补齐四种组合，并加入原始新版的重复对照和旧版同 tile 参考。[E9]

实验沿用 C1 的固定随机输入、同一个原生客户端和新版运行时。四种组合使用同一新版算法和代码对象；新增的一组只改一个四字节分支，保留通用尾处理，转向已有的四元素宽边界写回路径。每种路径四个独立进程，轮换顺序，共 24 个计时进程；每进程九个 graph 样本，每图 100 次 GEMM。全部进程在计时前后通过全元素 CPU 双精度参考检查，容差与首轮相同。GPU 始终使用已核验的 STABLE_PEAK；硬件计数另行采集，不使用 profiler 耗时。

| 路径 | 通用尾处理 | 写回 | 中位数 μs | 独立 VALU 每 dispatch |
| --- | --- | --- | ---: | ---: |
| A 新版原始 | 保留 | 标量 | 6.581 | 2874 |
| A 重复对照 | 保留 | 标量 | 6.584 | 未重复计数 |
| B | 跳过 | 标量 | 5.046 | 2544 |
| C 新增对照 | 保留 | 四元素宽向量 | 5.349 | 2537 |
| D | 跳过 | 四元素宽向量 | 4.489 | 2304 |
| 旧版同 tile 参考 | 旧版路径 | 四元素宽向量 | 4.451 | 2366 |

表中时间是四个进程中位数的中位数。按同一轮配对计算，标量写回下跳过尾处理节省 1.534 μs，向量写回下只节省 0.850 μs；保留尾处理时改向量写回节省 1.239 μs，跳过尾处理后则节省 0.555 μs。换言之，改写回的收益取决于尾处理是否还在。

四组交互项定义为 A−B−C+D，即比较“有尾处理”和“无尾处理”时改变写回方式的收益差。四轮交互项中位数为 0.682 μs，范围为 0.663—0.690 μs；同期 A/A 重复对照的配对差最大绝对值为 0.0172 μs。这个结果支持两因素存在相互影响。范围来自有限重复，不能当作置信区间或显著性检验。

![图 C1 GPU 因素交互](../../data/report-updates/readability-20261011/figures/04-gpu-interaction.png)

**图 C1｜GPU 四组对照揭示交互。** 两条线不平行，说明改变写回的收益取决于尾处理是否保留。点为 E9 的四个进程中位数的中位数；0.682 μs 来自逐轮配对计算，不能由四个汇总点直接相减。旧版虚线是同期同 tile 参考，接近该线不等于已经证明等价。首轮 E6 的数字保留在前表，未与本图合并。

### 用指令证据解释交互发生在哪里

独立计数中，每种路径三次 dispatch 的 VALU 都相同。四组相减得到 2874−2544−2537+2304=97。我们再检查实际选中的无激活直线代码段，得到下表；它不包含其他激活分支。

| 选中代码段 | 静态 VALU 条数 | LDS 读取指令 | 全局写回指令 |
| --- | ---: | --- | --- |
| 通用尾处理加标量写回 | 656 | 48 条 `ds_load_b32` | 64 条 `buffer_store_b32` |
| 通用尾处理加向量写回 | 319 | 8 条 `ds_load_b128` | 16 条 `buffer_store_b128` |
| 原始乘积加标量写回 | 334 | 无 | 64 条 `buffer_store_b32` |
| 原始乘积加向量写回 | 94 | 无 | 16 条 `buffer_store_b128` |

静态指令的交互项同样为 656−334−319+94=97，精确对应 48 条 `v_sub_nc_u32_e64`、48 条 `v_lshlrev_b32_e32` 和一条 `v_mov_b32_e32`。这把原因缩小到具体工作：标量写回不只增加全局写回次数，还让通用尾处理重复计算片上共享内存（LDS）的读取地址。

计时和指令数指向同一件事：通用尾处理配上标量写回，会重复计算 LDS 读取地址；改掉路径后，重复工作少了，耗时也降了。但我们还没有单独测出每类指令花了多少时间。标量指令、LDS 读取、等待和依赖关系也在变，不能把 0.682 μs 全算给 97 条 VALU。

## 附录 D 上游提交与设计取舍

前面的实验已经说明改哪些地方会变快，接下来要查这些变化是从哪次提交引入的。我们把实际构建中的源码、算法资源和指令路径与上游逐一核对。找到改动来源，和测出它在当前条件下花了多少时间，是两个不同的结论，证据强度也分别标注。

### 五个提交与已测行为的对应关系

安装源码、发布分支与归档构建信息已交叉核对。下表确认具体变化的来源；完整提交通常包含更多改动，只有重建并测量父子版本，才能得到整个提交的性能净影响。[E12]

| 上游提交 | 对应的具体变化 | 已核验的范围 |
| --- | --- | --- |
| PyTorch [f6ef243e](https://github.com/pytorch/pytorch/commit/f6ef243ef8b025cfb860666b8de2da6d1db46ad0) | 配置值 `user_override` 从普通属性改为 `ContextVar`；设置和恢复改用 `.get()`、`.set()` | 父提交与该提交的原始闭包回放，配置值可正确恢复 |
| PyTorch [de1f9fd0](https://github.com/pytorch/pytorch/commit/de1f9fd0e579deec08dff1b761d6c21f4424188f) | 设置和恢复时加入 `_mark_get_dict_dirty(k)` | 此函数进入真实热路径；本例读到空缓存后返回，没有重建字典 |
| PyTorch [b3ee252f](https://github.com/pytorch/pytorch/commit/b3ee252f1cb7fb6f3a80c775f6118975ba83a1da) | 设置和恢复时加入 `_hash_dirty_var.set(True)` | 哈希失效状态改为按上下文隔离，闭包快速路径也会标记失效 |
| ROCm [4c97c0dc](https://github.com/ROCm/rocm-libraries/commit/4c97c0dcde5fd5df2ed5c92a3017d7c9d62a65c4) | VALU 元素生成器和调用器改变边界写回宽度选择 | 固定参数下，父提交及旧发布版为宽度 4、16 组；该提交及新发布版为宽度 1、64 组 |
| ROCm [98aa2c31](https://github.com/ROCm/rocm-libraries/commit/98aa2c31e8c2d17f60c52047114fbf93e42962e9) | 删除该布局的旧 GridBased 小 tile 资源，加入新版 Equality 资源及其通用尾处理配置 | 已核对被删除文件、四个新候选和所测新版 32×64×16 配置 |

CPU 回放每次处理两个配置键，设置后再恢复。三个提交依次使调用数变为：2 次 override.get、4 次 override.set；再增加 4 次字典维护；最后增加 4 次哈希失效标记。最终每次 8 次 `ContextVar.set`、4 次字典维护，与真实任务调用跟踪吻合。回放执行的是提取的原始函数，依赖对象用于记录调用；它验证行为，不是完整框架性能测试。[E10、E12]

GPU 写回变化发生在 `NotLocalFullTileElementsVALU.__call__` 和 `globalWriteElements`。旧路径按 `min(VectorWidthA, maxGwvw, AssertFree0ElementMultiple)` 选择边界宽度，本例三个值均为 4；新路径生成候选宽度 4、2、1，普通内核的 `AdaptiveGemm=0` 分支保留 4、1，M 边界转入宽度 1。相关元素生成器文件在“父提交与旧发布版”“该提交与新发布版”之间分别逐字节一致。这解释了宽度变化的来源。E13 进一步在固定新版中修正该逻辑并重建、计时，补上源码到性能的干预证据；仍未测量这两个完整提交的净影响。[E12、E13]

资源提交删除的小 tile 包括 8×8×8、16×16×8、8×8×16、16×16×16。新增集合为两个预取配置不同的 64×64×16，以及 64×64×32、32×64×16。最后一个配置启用了 bias、逐向量缩放和通用激活支持，对应本例的通用尾处理。旧库其他算法早已支持这些功能，因此这里定位的是当前资源配置的引入，不能称为“首次加入尾处理”，也不能断言旧版同 tile 专用 Equality 文件由这个提交删除。[E12]

### 设计目标与可能非预期的代价

实验能告诉我们哪项变化让当前案例变慢，却不能直接告诉我们作者当时怎么想。改动有合理目的，不代表作者预料并接受了所有退化；公开说明里没有提到，也不代表作者从没考虑过。下面把公开讨论中的原话和我们的判断分开，前面因果树的证据强度不因此改变。

**配置隔离有合入前已知性能代价的直接记录。** 对应 `f6ef243e` 的 PR 中，评审者于 2026 年 3 月 29 日报告部分运行时基准增加约 5% 开销；作者于 3 月 31 日引用这条反馈，回应已更新性能预期文件 `expected_results.csv`，随后该提交于 4 月 1 日合入。这支持“作者知悉部分运行时开销后继续推进线程／上下文隔离改造”，但不等于有一份量化收益与代价的正式决策，也不能把这些基准的百分比套用到本文 G1。已知代价同样不意味着成本不可优化。[性能反馈](https://github.com/pytorch/pytorch/pull/173568#issuecomment-4150431235)、[作者回应](https://github.com/pytorch/pytorch/pull/173568#issuecomment-4158934290)、[合入提交](https://github.com/pytorch/pytorch/commit/f6ef243ef8b025cfb860666b8de2da6d1db46ad0)

其余几项改动为什么做、作者是否预料到代价，整理如下。“可能非预期”是我们的判断，不是作者自己承认的结论。

| 变化与因果分支 | 作者或评审明确说明的目标 | 对退化是否在预期内的判断 |
| --- | --- | --- |
| 字典缓存维护 `de1f9fd0`，CPU2、CPU5 | 避免每次导出配置都遍历大量键；作者报告一组大模型冷编译由 31.4 秒降至 31.0 秒，约快 1.3%。[PR #181159](https://github.com/pytorch/pytorch/pull/181159) | **可能遗漏了热调用代价。** 本文测到设置／恢复时增加维护，而当前路径没有重建字典。优化冷编译、增加热路径维护成本是代码与实验支持的取舍解释；未找到作者明确接受本类退化的表述，冷编译收益也不是本文复测结果 |
| 哈希失效隔离 `b3ee252f`，CPU3、CPU6 | 修复线程间错误复用配置哈希，并让快速设置／恢复路径正确标记失效。[PR #181651](https://github.com/pytorch/pytorch/pull/181651) | **维护行为是有意的正确性修复，具体性能代价是否被预料不明。** 不能把删除失效标记当成等价生产优化 |
| 小 tile 候选缺失 `98aa2c31`，GPU1、GPU2 | 修复 M=3、N=2073600、K=3 的特殊矩阵问题；列出的性能检查针对 3072 和 4096 阶大方阵。[PR #2753](https://github.com/ROCm/rocm-libraries/pull/2753) | **疑似非预期的小矩阵副作用。** 公开说明没有展示对本文这类小矩阵的性能权衡；这既不能证明作者有意牺牲它们，也不能证明作者未做其他测试 |
| 普通路径边界标量写回 `4c97c0dc`，GPU4、GPU6 | AdaptiveGemm 的目标是随尺寸改变写回宽度；评审要求功能可关闭，以免所有库代码体积增加。[PR #2511](https://github.com/ROCm/rocm-libraries/pull/2511)、[体积取舍讨论](https://github.com/ROCm/rocm-libraries/pull/2511#issuecomment-3500059607) | **较可能是非预期回归，但不是作者确认。** 功能与代码体积的取舍有直接记录，不能据此解释关闭 AdaptiveGemm 时本文测到的边界路径退化 |
| 通用尾处理，GPU3、GPU5 | 所测配置包含 bias、scale、activation 支持；这是已核验的功能配置，相关资源更新说明没有单独交代其小矩阵成本。[E12] | **意图未明。** 不能从功能通用化推导出“作者主动接受未启用这些功能时的开销” |
| 尾处理与标量写回的交互，GPU7—GPU9 | 本文确认两者共同增加地址计算，并出现时间交互。[E9] | **可能未被充分预料。** 没有作者知悉或接受这项交互代价的证据；0.682 μs 也仍不能全部归给 97 条 VALU |

AdaptiveGemm 的评审还提供了一条方向相反的证据：有人指出改动删除了非边界写回块，会使 `AdaptiveGemm=0` 的原路径退化；维护者回应关闭该功能的路径不应受影响，作者随后表示已补回相应代码。**这讨论的是另一处非边界问题，并非本文定位的边界宽度问题。** 它支持“维持普通路径行为是设计要求”，不能证明作者已经发现或修复本文所测回归。[回归反馈](https://github.com/ROCm/rocm-libraries/pull/2511#discussion_r2512369957)、[维护者回应](https://github.com/ROCm/rocm-libraries/pull/2511#discussion_r2512630144)、[作者修订说明](https://github.com/ROCm/rocm-libraries/pull/2511#discussion_r2513277832)

因此，配置隔离在其他公开基准中的部分开销属于“有记录的已知代价”，本文 G1 的具体损失是否被预料仍不能据此确定。小 tile 缺失、普通边界路径变化及热调用维护成本，是值得优先优化的疑似非预期副作用。修复应尽量保留线程隔离、缓存一致性、完整尾处理和大尺寸支持。入口布局效应尚未被证明导致原始升级退化，CPU8 也尚未定位到具体操作，因此二者不列入“作者未预料的升级回归”。这些意图判断不会把局部干预收益变成整个提交的净回归量。

## 附录 E 同一新版中的边界修复与小 tile 对照

直接改二进制分支，已经能看出两条路径确实耗时，但离可用的修复还差一步：把改动写进生成器后，收益还在不在？不换回旧库，只补小 tile，能不能同样提速？这轮实验固定新版源码提交、编译器、hipBLASLt 共享库、运行时和通用尾处理，对照两种生成器和三种候选配置。[E13]

边界修复只改变普通 VALU 内核的写回宽度下限：当 M 的对齐条件保证四元素写回合法时，不再退到宽度 1；对齐只保证 1 或 2 时保留对应宽度，AdaptiveGemm 路径不变。候选配置分成两种小 tile 干预，避免混淆其含义。

| 候选 | 人为改变的配置 | 用来回答什么 |
| --- | --- | --- |
| 新版原始 32×64×16 | 无 | 源码重建基线 |
| 受控缩小到 16×32×16 | 只把 ThreadTile 从 8×8 改为 4×4；wave32、4×8 workgroup、向量宽度、预取和尾处理保持一致 | 缩小 tile 在固定新版中的条件效果 |
| 恢复旧 16×16×16 配方 | 使用旧候选的 tile、wave64、预取和访存配置，接入新版参数协议与同一通用尾处理问题类型 | 补回旧候选配方的收益，不能称为纯 tile 尺寸效果 |

缩小 ThreadTile 后，VGPR 从 168 降至 72，LDS 从 14336 字节降至 7168 字节。这些是同一配置干预产生的结果，并非另外手调的因素；但各自贡献了多少时间，尚未拆分。恢复旧配方则使用 32 个 VGPR、4096 字节 LDS。所有候选都显式指定算法，未验证默认启发式会自动选中它们。

重建时遇到了一件容易误判的事：原始大 tile 的代码区与安装库逐字节相同，描述符也只差入口位置，但把它封装成较小的代码对象后，耗时却从同期安装库的 6.573 μs 变成了 7.707 μs。

我们试着只改候选的 stagger 映射参数，差距没有消失；保留实验元数据、换回安装库的代码对象，耗时又回到约 6.56 μs。问题因此指向封装或布局，计算指令本身没有变化。后面的 E14 又把范围缩小到入口布局，详见附录 G。实际加载地址、具体取指或缓存机制，仍未确定。

正式比较时，我们把六个内核变体分别链接到同一个代码起始偏移。这里说“指令不变”，是指每个变体在重链接前后不变，并不是六个变体的指令相同；修复写回、修改 tile，本来就会生成不同代码。入口相同，也不代表函数内部所有指令的位置或实际 GPU 加载地址都相同。

控制入口后，重建基线为 6.587 μs，同期安装库为 6.585 μs，配对差值中位数为 0.004 μs；原始代码重复对照的最大绝对差为 0.051 μs。前面的封装探索保留为单独证据，不混入下面的统计。统一链接偏移是实验控制，不是生产优化建议。

正式 C1 对照共六轮，每轮随机顺序运行六个组合、一个原始重复对照和一个安装库对照，共 48 个新进程。输入沿用冻结随机矩阵，alpha=1、beta=0；每个进程仍以一张含 100 次 GEMM 的图记录九个样本，计时不启用 profiler。表中为进程中位数的中位数。

| 候选配置 | 原始生成器 μs | 修复边界写回 μs | 原始 → 修复 VALU / dispatch |
| --- | ---: | ---: | ---: |
| 新版 32×64×16 | 6.587 | 5.300 | 2874 → 2537 |
| 受控 16×32×16 | 3.834 | 3.813 | 716 → 716 |
| 恢复旧 16×16×16 配方 | 4.047 | 4.051 | 241 → 241 |

按同轮配对，原始大 tile 上的边界修复节省 **1.286 μs**，六轮范围 1.258—1.335 μs。先修复写回，再受控缩小 tile，仍节省 **1.487 μs**，范围 1.480—1.516 μs。这分别确认了“生成器修复有效”和“写回修复后缩小 tile 仍有收益”。恢复旧小 tile 配方在写回已修复后也能节省 **1.249 μs**，范围 1.244—1.276 μs，证明无需换回旧库也能从补回候选中获益。这里的范围是重复实验的观测范围，不是置信区间。

不能把两项干预各自相对原始版本的收益相加：未修复时，受控缩小 tile 节省 2.760 μs；修复后只再节省 1.487 μs。四组配对交互为 1.272 μs，范围 1.238—1.332 μs。若按“先修写回，再缩 tile”的顺序计算，同一轮中的两段条件差值可以相加得到联合效果；分别取中位数后不要求严格相等。

C1 的原生 M=16 恰好填满 16×32 tile 的 M 方向，避开原来的标量 M 边界分支；N 方向仍可能不足整块。此时小 tile 上修复前后 VALU 均为 716，时间差仅 0.018 μs，未超出同期原始重复对照的波动，不能声称还有稳定的额外收益。

为了检查这个解释，我们只把原生列主序 M 改为 12，保持 N=16、K=32，让两种受控 tile 都存在 M 边界，并另做四轮对照。大 tile 从 6.565 μs 降至 5.336 μs；小 tile 从 4.167 μs 降至 3.816 μs，小 tile 的配对节省为 **0.351 μs**，四轮范围 0.339—0.358 μs，VALU 同时从 801 降至 716。这支持“C1 中缩小 tile 已避开原来的标量 M 边界分支，所以两项收益重叠”的机制解释。该补充尺寸按原生列主序接口列示，不与前面的行主序案例编号合并。

正确性检查包含六个组合的 C1 冒烟验证，以及 4×4×4、12×20×7、20×12×17、32×64×32、36×68×33、128×128×128 六个原生列主序形状，分别使用 alpha/beta=1/0 和 −0.75/0.5，共 72 项扩展检查；结果与双精度 CPU 累加参考相符，输出两侧哨兵未改变。所有计时也在前后核验结果。PMC 独立采集，每个组合的 20 次 GEMM 计数一致。检查覆盖了对齐边界和尾 K，但没有验证实际启用 bias、activation、scale、其他 GSU 或其他 GPU，仍不能直接当作通用生产修复。

这一轮验证了两件事：在新版源码里修写回有效，补回小 tile 也有效。但我们没有回退整个上游提交，也没有让默认算法选择自动使用新候选。后续 E14—E16 继续检查入口布局、队列状态和小 tile 预取；取指机制，以及寄存器、LDS、计算量各自占多少耗时，仍未拆清。

诊断修改的正确性只在指定输入、alpha/beta、尾处理和对齐条件下检查过；CPU 拆分固定了外层配置。下面列出尚未解释的差距与缺失对照，避免把局部归因当成完整修复。

### 相同机器码为何还会变慢 入口布局对照

源码重建曾产生约 1.13 μs 的额外差距，但指令内容没有变化。为区分入口位置与对象组成，我们重新链接同一个目标文件，逐字节检查目标函数，并核对描述符除入口偏移外保持一致。首批四轮、56 个进程扫描入口位置及对象组成；跟进批次另做四轮、52 个进程，将单内核入口移到三内核对象中的相同位置。两批都复用原生 C1、固定新版运行时和图重放协议，分别统计。[E14]

首批单内核入口为 0x10000 时，耗时 6.531 μs；改到 0x10100 为 6.109 μs，改到 0x11000 为 6.901 μs。指令内容没有变化，但执行时间随布局变化。把另外两个内核放在目标内核后面、保持目标入口 0x10000，耗时为 6.569 μs；同轮相对单内核的配对差值为 0.032 μs，范围 0.012—0.048 μs。该批基线重复对照的最大绝对差为 0.043 μs，其量级接近重复对照波动，不能解释原先约 1.13 μs 的封装差距。

跟进对照更直接地回答了原先的封装问题。

| 目标入口与对象组成 | 每次 GEMM μs |
| --- | ---: |
| 单内核，入口 0x1b600 | 7.670 |
| 原三内核对象，同入口 0x1b600 | 7.647 |
| 单内核，入口 0x25600 | 6.828 |
| 重排后三内核对象，同入口 0x25600 | 6.854 |
| 单内核，入口 0x10100 | 6.098 |
| 单内核，入口 0x20100 | 6.069 |
| 单内核，入口 0x30100 | 6.076 |

单内核也能复现原三内核对象的慢路径：在 0x1b600，同轮配对差值只有 0.022 μs，四轮范围 0.006—0.029 μs；在 0x25600，单内核相对三内核的配对差值为 −0.023 μs，范围 −0.039—−0.011 μs。相差 64 KiB 的若干入口位置也表现接近，例如 0x10100、0x20100、0x30100，以及另组 0x02d00、0x12d00、0x22d00。

因此，证据已从笼统的“封装有关”收窄为：**固定指令内容时，入口布局能够造成可重复的时间变化；改变对象包含多少个内核，并不是复现大幅变慢所必需的条件。** 这些地址是 ELF 中的虚拟偏移，尚未记录 GPU 实际加载地址。相隔 64 KiB 的近似重复只是一条线索，不能据此认定具体缓存容量、索引冲突或取指单元故障，也未证明布局是原始软件栈升级退化的原因。

### 单调用 event 剩余测到了什么 队列对照

此前配置外移后约 1.50 μs、再改变 fullgraph 维护后约 0.57 μs，来自特定批次与测量方式，并不是两个固定组件的耗时。新的对照保留 G1 的冻结输入，在新旧栈各运行四个独立进程；固定相同 CPU 亲和性，在每个进程内随机测量原始包装、两种包装干预、直接生成程序及空调用。每种路径交叉比较新建或预初始化 event，以及空闲队列或预先排入 GPU 工作。[E15]

排队条件先重放包含 100 次生成程序调用的图，再依次提交开始 event、被测函数和结束 event。它保留真实函数调用，但让 CPU 有时间在 GPU 执行计时起点之前提交后续工作。主计时不插入 CPU 时间戳；提交完结束 event 后查询开始 event，38400 次检查全部显示尚未执行。另设带 CPU 时间戳的诊断采样，保留在独立字段，不混入主结果。

下表采用预先初始化的 event。每个进程对每种组合做六轮、每轮 80 个样本；先取进程中位数，再计算同轮新旧配对差值。

| 调用路径 | 空闲队列中新版 − 旧版 μs | 预先排队后新版 − 旧版 μs |
| --- | ---: | ---: |
| 原始编译后调用 | 7.283 | 0.177 |
| 静态配置外移 | 5.217 | 0.160 |
| 再改变 fullgraph 维护 | 4.077 | 0.164 |
| 直接调用生成程序 | 0.285 | 0.128 |
| 空调用对照 | 0.008 | −0.047 |

这些数字属于新批次，不能用来替换或相加到首轮的 0.57 μs。此次“静态配置外移并改变 fullgraph”的差距，在空闲队列中四轮为 2.410—4.411 μs，排队后为 0.125—0.281 μs。再减去同轮直接调用生成程序的新旧差距，得到包装路径额外差距的描述性对照：空闲时配对中位数 3.693 μs，排队后为 0.019 μs，范围 −0.073—0.134 μs。这一步不是完整时间分解，而是检查包装路径是否仍具有独有的新旧差异。

**剩下的大部分差距，会随 CPU 提交和 GPU 队列的先后时序改变，不能看成 kernel 或 event 固定多花的一笔时间。** 预先排入工作后，各种包装调用的新旧差距接近直接调用生成程序的结果，空调用也没有相应变慢。因此，很难再用“event 本身多了一笔固定开销”解释全部残差。

但排队还会改变缓存和调度，所以剩下约 0.16 μs 仍不能指定给某个 runtime 函数。GPU 等待 CPU 的空隙，究竟出现在 kernel 入队前，还是结束 event 入队前，也没有完全分清。CPU 完整调用的成本没有凭空消失，只是未必全部落在这段 GPU event 计时内。

### 小 tile 配方差在哪里 局部预取的独立贡献

E13 中恢复的 16×16 配方比受控 16×32 配方慢约 0.239 μs。两者不只 tile 不同，还改变了 wave、预取和访存配置。新的实验以恢复配方为起点，在同一新版和同一边界修复下逐项改变可构建配置，并把目标入口统一为 0x10000。恢复配方与受控 16×32 的机器码均与 E13 对应基线一致。[E16]

八个可执行配方均通过计时前后数值检查及输出哨兵检查，另通过 32 项含 M 边界、尾 K 和非零 beta 的扩展验证。首批四轮、36 个进程包含恢复配方的重复对照。

| 配方变化 | 每次 GEMM μs | 相对恢复配方的配对节省 μs | VALU / dispatch |
| --- | ---: | ---: | ---: |
| 恢复配方，PGR=1、PLR=0 | 4.052 | — | 241 |
| 只将全局预取 PGR 改为 2 | 3.993 | 0.059 | 245 |
| 只开启局部预取 PLR=1 | 3.772 | 0.282 | 241 |
| 同时 PGR=2、PLR=1 | 3.708 | 0.345 | 245 |
| 改为 wave32 并调整线程组织，保持 16×16 tile | 4.223 | −0.162 | 385 |
| 改为内联激活处理代码 | 3.991 | 0.063 | 237 |
| 关闭 ExpandPointerSwap | 4.049 | 0.003 | 245 |

局部预取的单项收益为 0.282 μs，四轮范围 0.260—0.300 μs；同时调整两类预取节省 0.345 μs，范围 0.332—0.363 μs。只开启局部预取时，tile、wave64、访存宽度、241 条 VALU、32 个 VGPR 和 4096 字节 LDS 都保持不变。生成汇编改变了 LDS 读取、寄存器使用和计算的安排。收益因而不能用“VALU 更少”或“资源占用更低”解释；当前证据支持预取配置的条件影响，尚未逐周期拆开等待、依赖及内部布局的贡献。

为避免再次被某个代码位置误导，另做四轮、48 个进程，将恢复配方、PLR=1、两类预取调整及受控 16×32 配方分别放在三个入口偏移上复测。

### 预取为何变快 只改变等待阈值的对照

E16 说明局部预取有效，但同时改变了读取安排、寄存器使用和等待方式。要补齐 GPU14，需要保留这些代码形态，只改变其中一个可控制因素。E17 以同一 PLR 内核为起点，将部分 `s_wait_dscnt` 的非零阈值改为 0；这要求对应 DS 操作完成后再继续。该指令等待计数器下降至指定上限，依据为 [AMD RDNA 4 指令集文档](https://docs.amd.com/api/khub/documents/uQpkEvk3pv~kfAb2x~j4uw/content)。

我们分别收紧阈值为 4 的 50 个静态位置、阈值为 5 的 10 个位置、两组合并，以及全部 65 个非零位置。这里是静态位置数，不是一次运行执行这些指令的次数。重新构建的原始内核与 E16 的函数机器码完全一致；干预变体与它相比，只改变等待指令的立即数，函数长度、每条指令的位置及资源描述保持相同。主批次入口固定为 0x10000，每组四轮随机配对，并包含相同内核的重复对照。[E17]

| --- | ---: | ---: |
| 原始 PLR | 3.763 | 0 |
| 相同内核重复对照 | 3.764 | 0.001 |
| 仅收紧阈值 4 | 3.981 | 0.218 |
| 仅收紧阈值 5 | 3.815 | 0.053 |
| 收紧阈值 4 和 5 | 4.036 | 0.274 |
| 收紧全部非零阈值 | 4.042 | 0.277 |
| 未开启 PLR 的配方 | 4.049 | 0.285 |

![图 G4 等待阈值的独立干预](../../data/report-updates/readability-20261011/figures/11-wait-threshold.png)

**图 G4｜保留预取代码，只收紧等待，就抵消了大部分收益。** 主批次全收紧的配对增加范围为 0.276—0.282 μs；同期相同内核重复对照最大绝对差为 0.000810 μs。阈值 4 与阈值 5 的时间交互中位数为 0.009 μs，范围 −0.003—0.013 μs，不能把两组当作精确可加的固定成本。

独立复核将入口换到 0x10000、0x10100、0x11000，全部等待收紧后分别回升 0.278、0.258、0.286 μs，12 个配对均变慢。因此，这个效果不依赖唯一的入口位置。五个变体的独立 PMC 各检查 20 次 GEMM，均为 241 VALU；32 个 VGPR 和 4096 字节 LDS 保持相同。40 项扩展数值与哨兵检查通过，包含边界尺寸、尾 K 和非零 beta；所有计时进程也在前后核验结果。

**GPU14 现在可以确认的是：在当前内核和输入下，等待阈值确实影响了耗时。** 保留其他预取代码、只收紧等待，就会抵消大部分收益，因此不能再只说“调度看起来更好”。

主批次中，未开启 PLR 与收紧全部等待的变体还差 0.007 μs，配对范围为 −0.001—0.013 μs；换三个入口位置复核，残差中位数分别为 0.018、0.003、0.001 μs，后两个位置仍有正有负。这些结果很接近，但还没有证明性能等价，更没有测出每个等待点具体占几个周期。其他尺寸是否同样受益、整套配方的差距能否逐项分清、默认算法能否选中它，仍待验证。

### 单调用差距落在哪里 移动计时边界并核验观测扰动

E15 用排队消除了大部分包装路径差距，但不能区分等待发生在矩阵乘提交前还是返回后。E18 保留 G1 冻结输入及配置外移、fullgraph 干预，在新旧栈各运行四个独立进程。每次只记录两个预初始化 event，分别将开始、结束或两者移动到生成程序实际调用的矩阵乘 API 两侧。所有模式交叉比较空闲与排队状态，并设置挂钩外层、未挂钩外层和直接生成程序对照；每个条件四轮随机顺序、每轮 80 个样本。

下表先计算各路径的“新版减旧版”，再减去直接生成程序的对应差值，得到包装层额外差距。边界改变了测量对象；各行不能相减后当作互不重叠的 CPU 成本。

| --- | ---: | ---: |
| 未挂钩，原始外层区间 | 2.106 | −0.004 |
| 挂钩，仍测外层区间 | 4.255 | −0.029 |
| 仅开始 event 紧贴矩阵乘 API 前 | 2.489 | 0.024 |
| 仅结束 event 紧贴矩阵乘 API 后 | 2.681 | 0.020 |
| 两个 event 紧贴矩阵乘 API 两侧 | −0.175 | −0.010 |

![图 G5 单调用计时边界与观测扰动](../../data/report-updates/readability-20261011/figures/12-event-boundary.png)

**图 G5｜大幅差距依赖外层区间，但观测本身会改变它。** 图中的“移入 mm”指将 event 从外层边界移至矩阵乘 API 的前后两侧；没有在 GPU 内核内部插入计时指令。 两个 event 都移入后，包装调用本身的新旧差距为 −0.040 μs，四轮范围 −0.430—0.091 μs；大幅正向差距不再出现。排队条件共 25600 次确认开始 event 尚未执行。只移动一端仍有明显差距，说明不能把整个现象简单定位为“结束 event 太晚”。

关键限制来自控制组：不改变外层计时边界，仅增加用于移动 event 的 Python 钩子，就把包装调用的新旧差距从 2.076 μs 放大到 4.301 μs。因此，钩子下的前后差值不是原始路径各段成本。四轮挂钩外层差距范围为 0.630—5.501 μs，波动也明显大于未挂钩的 1.890—2.390 μs；全部样本保留，没有按结论删去异常轮。

为进一步核对方向，我们在通过容器 CPU 集合约束及采样前后亲和性断言的另一批八个进程中，只用 CPU 时间戳，将完整主机调用分成进入矩阵乘 API 前、API 内、API 返回后三段，并保留未挂钩对照；这批主机时间不混入 event 数据。空闲条件下，扣除直接生成程序后，三段额外新旧差距分别为 1.978、0.381、0.180 μs。它更支持继续检查提交前路径，不能支持“新增开销主要来自返回后收尾”。但插桩总差距为 2.702 μs，未挂钩仅为 1.191 μs，观测扰动再次出现。单样本的三段之和等于总时间，分别取中位数后不要求严格可加。

首次主机分段采集中，一个旧栈进程结束时的 CPU 亲和性从单核变为全部核心；该批还有排队计时反向大波动。整批八个进程作为控制失败记录保留，不用于上述确认结论。随后整批重跑，用容器 CPU 集合限制在同一核心，并在每个采样条件前后断言亲和性；全部通过。确认批排队条件下的插桩额外总差距为 3.488 μs，范围 2.097—3.820 μs。STABLE_PEAK 控制的是 GPU，没有锁定 CPU 频率，因此主机分段仍不能排除频率与调度影响。

**CPU8 的排查范围缩小了，但还没有查完。** 移动计时位置、改变队列状态，都说明调用包装、CPU 提交和 GPU 执行的先后时序会影响差距。我们不能把这笔差距都算成 kernel 的固定成本，也不能把插入计时代码后测出的分段差值，当成原始 CPU 路径各段真正增加的耗时。

后来的 E19 去掉内部计时钩子，直接改源码检查前置逻辑，但重复对照仍有足以干扰细分判断的波动。因此，我们不再继续加 Python 钩子，或扩大删除范围，强求一个唯一答案。

### 哪些因果边有了新证据

E14 对应 GPU10—GPU11，E15、E18 对应 CPU7—CPU8，E16、E17 对应 GPU12—GPU14。两组实验的进展并不相同：E17 单独改了等待阈值，测到了它的作用；E18 改变计时位置后，缩小了问题范围，却也发现 Python 钩子会扰动结果，不能拿它给原始路径分摊耗时。因果树分别记录这些进展，不把所有做过的实验都算成已经完成归因。

### 最后一轮检查后为什么决定停下

针对 CPU8，E19 最后做了一轮不加内部计时钩子的源码对照。G1 输入保持不变，沿用配置外移和 fullgraph 改动，分别测试原包装器、按原样重建的源码、绕过四项新旧共有的 tracing/export 检查、绕过新版独有的嵌套编译检查，以及同时绕过两组检查。

这些诊断变体只在相关模式均未启用时运行。生成程序、输入 guards、状态保存恢复和清理代码保持原样。原样重建的字节码、异常处理表及名字表都与原函数相同；所有变体的输出检查通过，也没有新增生成程序。但这仍然是在固定场景下删去部分逻辑来定位，不能视为保持全部原有行为、可以直接部署的优化。[E19]

确认批次为四轮新旧进程配对，每个条件六轮随机顺序、每轮 100 个样本；外层 CPU 计时与 GPU event 分开采集，没有在矩阵乘内部加入钩子。另一个新版预检进程不混入确认批。下面均为各进程六轮中位数的配对差，再取四对中位数；范围是观测范围，不是置信区间。

| 空闲队列中的对照 | 配对中位数 μs | 四对范围 μs | 可支持的判断 |
| --- | ---: | --- | --- |
| 新版原函数 − 原样重建，event | 0.250 | −0.020—1.070 | 代码重建及测量条件的对照并非始终接近零 |
| 新版原函数 − 同函数重复，CPU | 0.175 | −1.591—0.987 | 完全相同函数也存在足以影响细分结论的波动 |
| 新版重建 − 绕过共有检查，event | 0.410 | 0.250—0.680 | 有节省方向，但不足以越过全部对照波动并给出独立份额 |
| 新版重建 − 绕过新增检查，event | −0.085 | −1.040—0.060 | 不支持该检查单独解释大幅残差 |
| 新版重建 − 绕过全部上述检查，event | 0.475 | −0.730—0.560 | 联合删减的效果也不稳定，不能拿中位数作收益预算 |

原包装器相对生成程序直接调用的额外新旧 event 差距，在本批空闲队列中为 4.020 μs；两版都绕过相应前置检查后仍为 3.330 μs。这些是本批描述性结果，不能与 E18 合并，也不能据其差值宣称已经解释了固定比例。CPU 亲和性固定为 CPU0，但 CPU 频率未锁定；本研究不进一步猜测波动来自哪一种主机机制。

这轮排队实验还没有完全满足控制条件：28,800 次检查中，有 21 次未能确认计时起点仍在等待执行，全部发生在旧栈进程。因此，整个排队分支都不用于确认结论，原始样本全部保留；不能只删掉这 21 个样本，就当作控制检查通过。

此前 E15、E18 的有效队列证据不受影响，但 E19 没能据此提高 CPU8 的证据强度，也没有把残差定位到某个具体 runtime 函数。

最后，E20 检查了几种改法在更多输入和尾处理组合下是否算对。原大 tile、修好边界写回的大 tile、修好边界写回的受控小 tile，以及开启 PLR 的旧小 tile 配方，分别运行 16×16×32、12×20×7、36×20×65、32×64×32 四个原生列主序形状。每个形状测试无尾处理、ReLU、bias、bias+ReLU，使用 alpha=−0.75、beta=0.5。

共 64 项检查全部通过：输出与 FP64 CPU 参考值相符，输出前后的哨兵也未改变。这批没有计时，不能据此增加性能收益结论；scale、GELU、其他 GSU、默认候选选择及任意形状，都不在覆盖范围内。[E20]

**排查到能指导软件修复，就可以收束，不必解释硬件的每个周期。** 如果新实验可能改变修复选择、收益判断，或排除足以推翻主结论的其他解释，再重新启动对应分支。

## 附录 H 从诊断到修复的验收要求

目前已经知道该改哪里，但定位时删掉的代码，不能原样作为生产修复提交。

CPU 侧应减少重复的配置设置、恢复和状态维护，同时保留嵌套作用域、配置变化、异常恢复、并发调用及 fullgraph 行为。本例没有发生哈希重算或字典重建，因此优化不应围绕这两项并未发生的工作展开。

E18 的结果提示，应优先检查矩阵乘提交之前的代码，但先要解决测量钩子的干扰，不能照着钩子测出的分段数字估算收益。E15 也说明，优化后的单调用 event 时间仍要结合队列状态看，不能把一个计时区间里剩下的差距都归给内核。

GPU 侧，修边界写回、补小 tile，都已经在固定新版中测到了收益。真正落地时，要检查对齐条件、完整尾处理功能，以及默认算法能否选中这些候选；调优时还要记录代码对象布局，避免把封装带来的差别算成算法收益。

小 tile 也不必只选一个答案。E13 中，受控缩小的 tile 比恢复旧配方更快；E16 只调整旧配方的预取，就能反转这个差距。E17 又发现，保留其他代码、收紧等待，会抵消大部分收益。因此，后续值得在小 tile 候选中继续调预取和等待，但必须保证数据依赖正确，不能认定 wave32 或原样恢复旧配置就是唯一方案。布局敏感性还要复核，其他尺寸和功能组合是否受益，也需另测。

这些发现不支持“一律关闭 hipBLASLt”或“删除输入检查”这样的处理。我们也尝试过把旧库预加载到新版 Torch，但新版 rocBLAS 需要的符号在旧库中不存在，导入就失败了，没有得到可比较的性能结果。

同一新版中，修边界写回和补小 tile 的对照已经完成，E20 也补做了一些 bias/ReLU 正确性检查。完整功能、默认算法选择和跨尺寸收益，则留待修复验收。CPU 优化同样要保留配置隔离和失效标记的正确行为，不能直接删除维护代码。

这次机制排查到此收束。逐条指令解释耗时、二分出完整提交的净影响，都不再作为本报告的完成条件。

这次最值得带走的经验是：同样表现为“矩阵乘变慢”，时间可能花在完全不同的地方。先分清提交与执行，再替换组件、逐项改代码，才能找到值得修的地方。没有解释清楚的差距，也应留在对应节点上，让读者看得到。
