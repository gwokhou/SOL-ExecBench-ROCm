## 3. B 线：把旧证据和当前执行版本分开

B0 的每条记录至少包含：能力/结论、原 source SHA、receipt 与工件路径/hash、
当前 owner、合同/运行时身份、复用检查入口、复用或刷新的理由。
使用 [release_environment](../../src/sol_execbench/core/scoring/release_environment.py)、
[资格链](../../src/sol_execbench/core/scoring/release_solar_qualification.py)、
[语义身份](../../src/solar/verification/execution.py) 的真实规则；不能凭“改动不大”手工认定有效。
文档改动、源码提交漂移和语义运行时漂移也不能当作同一种身份条件。

B1 固定：执行源码及相关路径清洁性、依赖锁、Python/Torch/ROCm、容器镜像 digest、
mapper allowlist/二进制摘要、设备 UUID/配置、语料/规则/checks 摘要、IR 路径、
超时、线程数、并发、内存与总活动预算。实际设备字段在 B2 准入时核验，差异使冻结失效。
相关 Ruff、format check、ty、耦合/可读性/契约检查和 CPU 测试范围与结果均留存；
测试沿用仓库 worker 上限，不用 `-n auto`。历史测试计数不作为必须复制的目标值。

B2 的执行与验收顺序：

1. 按现行设备/时钟/所有权门禁准入，确认容器缓存与所需工具可用；环境失败单列，不算数学失败。
2. 复用已有代表槽定义，检查 R06 动态索引、R04 attention、已完成过回放的小型 conv，
   以及预登记的域外拒绝。检查真实语义回放与资格身份，不仅检查 FakeTensor 取图。
3. 在相同冻结身份下执行 AKA make_fx 的 `qualify-static → canary → full`。
   预期分母为现行 manifest 的 163 项及派生 canary 112 项；若 manifest 变了，回到 B0，
   不静默沿用这些数字。成功要求链与全部门禁完整，不接受跨 SHA 拼接。
4. 单列完整 formal-analysis 的证据覆盖。大卷积回放 miss 仍留在缺口账本；本轮默认不重试，
   不把 163 ready 写成 163 个完整容量分析通过。若必须研究该 miss，另立有内存上限的任务。

B2 不要求重复历史所有 mapper/GPU 实验，也不要求补齐 torchview 全分母资格。
当前 source identity 使资格链不能复用时，刷新所需链；能通过现行验证器严格复用的独立证据不重复采集。
产物须同时给出“集成基线是否合格”和“已知未证实范围”，不重发历史官方分数。

## 4. E 线：裁判辨错实验

本轮聚焦数值/语义辨错，沿用既有可信 reference、输入唯一性与计时完整性保护。
它不是对任意恶意原生代码的安全证明，也不以此宣称全面优于上游 LLM judge。

### 4.1 固定小分母与独立 oracle

沿用既有三个任务各 w0–w2 的 shape/dtype/checks；原工作负载文件不改。
诊断输入单独派生并绑定原 workload、输入生成器与实际量化后的输入摘要。

| 任务 | 本轮固定范围 | 4 个输入族 |
| --- | --- | --- |
| [GEMM](../../problems/AMD_AKA/torch2hip/l1n2_standard_matmul/workload.jsonl) | BF16，3 个现有 `(M,K,N)`；原容差 .0125 | 普通随机；域内动态范围/尺度失衡；互补支持与微小可表示非零；强消去与共同置换 |
| [reduction](../../problems/AMD_AKA/torch2hip/l1n47_sum_reduction/workload.jsonl) | FP32，现有归约长度 256/64/4096；原容差 1.25e-5 | 全正；正负消去；大小量贡献；顺序置换 |
| [LayerNorm](../../problems/AMD_AKA/torch2hip/l1n40_layernorm/workload.jsonl) | FP32，现有 N=256/1024/128、eps=1e-5；原容差 1.25e-5 | 大共同偏移与小方差；近常数；方差接近 eps；非平凡 weight/bias |

预登记 3 任务 × 3 shape × 4 输入族 × 3 实例 = **每跨任务候选策略组108个逻辑case**。
E0 冻结4个策略组（12个单任务实现），总计432个候选—case单元；单任务候选消费36个case。
每族 2 实例供开发、1 实例留出：72 开发、36 留出。E0 固定实例派生与保管方式；
E1 完成后封存候选和判据，才允许 E2 打开留出。3 次独立进程复现是同一逻辑 case 的重复，
不扩大样本量；实际调用数再乘候选数和协议要求的迭代数，在 B1 预算中明确。
留出一旦用于修规则便标记已暴露，后续确认使用新预登记实例，不再称其盲测。

oracle 从候选实际收到的量化输入求值，写清输入量化、累加、输出/中间舍入语义和误差预算。
使用解析/精确小例及独立高精度路径交叉检查；高精度不自动等于真值。
先验证比较器不会因 FP32 转换抹掉需检测的差异。超出 oracle 可判定区间的 case 标为不确定，
不可强判候选错误。LayerNorm 不套 BLAS A/B/C 等级，变换后的浮点结果不要求逐位相同。

### 4.2 对照、判定与开销

每任务至少固定四类候选：已验证正确实现；故意遗漏计算/参数的语义突变；
有明确机制的数值弱化实现；合法浮点重排或自适应 fallback。
E0 必须逐候选写明适用域、应触发的 case、原契约预期和诊断预期，不能把所有弱精度算法都标成违规。
复用 [custom_inputs](../../src/sol_execbench/core/bench/custom_inputs.py) 和
[reference_service](../../src/sol_execbench/core/bench/reference_service.py)，不把参考输出交给候选。

每个 case 同时记录两个互不覆盖的结论：现行 evaluator verdict，以及独立诊断 verdict。
诊断分类为原契约违反、仅更强保证不成立、域外、不确定、通过；统计漏检和误拒时分开分母。
特别保留“符合原容差、丢失某个小量”的反例，它说明契约边界，不自动构成作弊。

E2 必交：按任务/输入族/候选类别的判定表，预设缺陷检出数/总数，合法对照误拒数/总数，
不确定与域外数量，以及每个反例的输入/输出/源码/hash。无独立标签的 case 不进入检出率分母。
重复结果不一致时给出全部重复记录，不用多数投票掩盖。

完成正确性部分后，按冻结输入与候选做配对成本测量：现行检查成本、附加诊断成本、
reference/IPC 成本、总墙钟、峰值内存及重复波动。编译/预热与稳态调用分列，
不从诊断计时生成官方分数。预算在结果揭示前固定；本轮不设未经测量依据的性能收益承诺。

**实验有效性验收**：每策略组108个逻辑case全部有身份、判定或明确的未完成原因；
输入域与 oracle 自检通过；预登记/留出边界可核对；无缺行或事后改阈值。
有效实验可以得出裁判未达标的结论。

**裁判达标条件**：预登记、可判定且属于原契约违反的缺陷全部被现行 gate 检出；
合法对照零误拒；目标诊断反例得到预登记的独立分类；三次复现一致。
任何一项不满足就登记具体漏检/误拒/不稳定，不把调整后的同组结果当初次确认。
这仅是固定小样本验收，不能外推全域错误率。正式检查或评分升级由 D0 后另行提案。

## 5. C 线：LLM_CORE 分阶段覆盖矩阵

### 5.1 分母和接入先于扫描

C0 选择**一个已验证 gfx1200 配置、profile=core、两条显式固定 IR 路径**。
全 36 个 Definition 先做清单，非 core 标为 profile 外；core 内按生产生成规则纳入或拒绝。
遵守 manifest 的 profile 最小生成数量门槛，未达到时不能称合格 target view。
成功生成数为 G，固定 workload 分母 N=9G，主矩阵为 **2N 行**；其余 Definition 在清单中保留理由。
不能写死 36×9，也不能从被拒绝的 Definition 挑单槽补入。
**C0 冻结细化**：当前 core 恰20项且最低门槛20，合格视图必须G=20、N=180、双路径360行；
不足20只交付不完整生成诊断，不缩减本次合格矩阵分母。目标固定 standard-16gb 配置模板，仍需实测验证。

现有 [corpus_readiness](../../src/sol_execbench/core/solar_bridge/corpus_readiness.py) 和发布资格链
直接加载 `AKACorpusManifest`。C1 需接通已验证 LLM_CORE target view 到现有
[stage worker](../../src/sol_execbench/core/solar_bridge/runner.py) 与
[analyze_workload](../../src/sol_execbench/core/solar_bridge/analyzer.py)，
保留 Definition/Workload/规则/target identity；不得伪装成 AKA 或绕过生产验证器。
新增报告如需独立序列化，归属相应 domain registry；不建立兼容影子注册表或第二套语义转换器。

C2 使用 [生产生成入口](../../src/sol_execbench/core/dataset/corpus.py) 的测量容量与整数容量类规则。
容量分配探针属于 GPU 活动，B2 前不得执行；可复用证据必须经现行身份检查。
冻结后 OOM、慢例或不支持项不能触发原地缩放、删槽或换 target view；新视图属于新活动。
容量模板不等于已观察硬件，target view 也不等于 SOLAR 形式资格。

9 槽全部由评测侧扫描；开发/留出角色不合并。C1 和判据在打开留出结果前冻结，
不向候选开发提供其具体形状或逐例结果。必须维护暴露记录；已用于覆盖修复的留出项，
不能再作为后续修复的独立确认集。语料规则公开，不能把该隔离描述成密码学保密。

### 5.2 每行记录及验收

| 阶段/维度 | 必须区分的证据 |
| --- | --- |
| 输入与提取 | target/workload/路径身份、取图结果；make_fx 内部声明式 real retry 单列，不与跨 IR 自动回退混淆 |
| 转换 | 算子/属性/控制流的支持或拒绝理由；不能把 adapter 缺口归成算子缺口 |
| 数值与梯度验证 | 分列 forward 数值、gradient、alias/mutation 等现行合同要求；不适用需明确合同依据，forward-only 本身不豁免转换梯度检查 |
| 外部读取 | 已证明、未证明及所缺证明词汇，不能用成功取图代替 |
| 容量分析与三视图 | formal bound 身份、资源计数、unfused/ideal_fused/cache_aware 分别可用性及原因 |
| 资源成本 | 各 stage 墙钟、host RSS/device 峰值、mapper 预算与超时；未测值显式缺失，不填 0 |

报告归一状态包括 passed、unsupported/unproved、failed、not_reached、
not_applicable、budget_exhausted、infrastructure_error，并保留原始 status/reason code。
这是报告层分类，不能替换生产协议词汇或把 refused 变为 pass。
timeout/OOM 是预算或资源结果，不是数学不支持；worker 意外崩溃必须排查，不自动计为有效完成。

C3 先逐 Definition smoke 槽检查执行器和预算，再展开同一冻结分母的其余槽；
扩展只改变执行顺序。未跑的行保留 not_reached 与原因，活动判 INCOMPLETE。
每个达到相应阶段的槽使用相同预登记资源政策；不得只挑容易项做容量分析后宣称全分母完成。

验收要求：

1. 36 条 Definition 清单完整；2N 行唯一且与封存 target view 精确对账，重试不增加分母。
2. 每行各阶段均有结果或合法的阻断/不适用原因；unsupported/unproved 可以是有效覆盖发现，
   但基础设施失败和活动预算用尽不能包装成覆盖研究完成。
3. 两路径共同成功项逐项比对资源计数和可用视图；差异定位到输入/图/计价/证据层，不取更好结果拼成新路径。
4. 按 operation family、profile、槽角色、路径、阶段汇总计数和成本；make_fx 为近期主线，
   torchview 保留独立比较。主线选择不等于修改公共默认 backend，也不要求两路径凑齐相同通过数。
5. 每个缺口有最小复现、受影响 Definition/槽数、所属层、证据路径、建议任务与验收样例。
   按语义重要性和受影响 Definition 排序，不让多槽重复把单一模式权重放大。

通过标准是矩阵完整、证据可核验、缺口可行动；**不要求 100% ready/formal**。
本轮只覆盖 core 和一个实测配置，其他 profile 仍为未测，不能推出跨容量/跨硬件泛化。

## 6. 预算、产物和迭代出口

E0/C0 已固定 case/候选/工作量和研究活动停止预算；B1 将现行 stage timeout、mapper 线程/并发政策、
host/device 内存上限、磁盘和 GPU 总窗口固化为执行配置。数值须来自现行限制与已登记证据，
或明确标为预登记的研究停止上限；不能留空开跑，也不默认抬高现有基线。已有 7200s mapper 超时只说明既有个例成本，
不承诺 LLM_CORE 每行可在同样成本完成。

到达预算或遇到未知崩溃：保存有界证据、停止受影响批次、标 INCOMPLETE，CPU 归因继续；
修复后使用新版本/新活动，未暴露项是否可复用按精确身份判断。GPU 使用现行 UUID L1/L2 锁、
时钟恢复和进程组排水协议，清理并恢复后才交接下一活动。禁止裸跑已知大卷积回放。

建议证据根为未提交的 `data/outputs/solar-next-iteration/<run-id>/`，内含：

- `baseline/`：身份/复用台账、源码差异、检查结果、资格回执索引与已知缺口。
- `judge/`：预登记、暴露记录、候选/输入/oracle 摘要、逐例结果、成本与混淆表。
- `llm-core/`：target view、Definition 清单、2N 行矩阵、原生产工件引用、差分和缺口表。
- `decision/`：三线终态、主张—证据对照、后续任务及明确未取得的证据。

这些是拟交付目录，不是当前已有工件；命名不赋予 schema 或发布权威。
提交的文档只记录摘要与索引，敏感输入和运行输出不入 Git。

按四个里程碑推进：**M0 规格冻结**（B0/E0/C0）→ **M1 执行基线**（E1/C1/B1/B2）
→ **M2 两项证据报告**（E2/C2/C3）→ **M3 决策**（D0）。不设未经测量的 GPU 完成日期。

D0 的后续选择规则：

- 原契约漏检/合法实现误拒：优先开最小修复及新留出确认任务；诊断更强只产生新契约提案。
- 高价值 LLM_CORE 模式受阻：优先解决已定位的 native-op、验证、读取证明或回放内存问题。
- 两路径对核心模式有共同系统性前端缺口：才启动 L3-d 可行性设计；JAX 或任意源码输入需求须另有真实消费者。
- 高阶多输入 einsum DP、符号化 Orojenesis、多架构真机、稀疏峰值等继续条件性排队；不因上游存在便自动补齐。

本轮最终可承诺的是有明确适用范围的基线、辨错证据和覆盖地图；正式评分改变、
LLM/Affine Loop/JAX 前端、优化内核生成及跨硬件实验均需之后独立立项。
