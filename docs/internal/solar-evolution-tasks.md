# SOLAR 演进：阶段 1–3 可执行任务规格

制定日期：2026-10-20。输入是[阶段 0 能力、假设和基线](solar-evolution-stage0.md)与[验收样本清单](solar-evolution-acceptance.md)。本文定义 BASE-01 及阶段 1–3 的任务规格和验收要求。仓库级进展只在 [HANDSOFF](../../HANDSOFF.md#solar-evolution) 维护。

2026-10-23 已完成 BASE-01 原始 CPU 前置工作，结果见[改进前基线报告](solar-base01-cpu-2026-10-23.md)。2026-10-26 已按当前工作树和更新后的规则完成[CPU 复采](solar-base01-cpu-2026-10-26.md)，保留计量差异与一项既存回归失败。下文保留任务规格；实际实施进度只由 HANDSOFF 维护，本次复采不推进阶段 1–3。

优先级：`BASE-01` 为 P0 前置；阶段 1–3 为 P1，按依赖推进。这里的 P0 指演进工作的前置项，不是历史资源审计 P0。任务编号是文档引用号，不是公共 API、命令或 schema 标识。下文接口及工件名描述职责，实施时再确定公开名称并同步所有消费者。

## 2. BASE-01：先取得未修改计量的运行基线

**范围与交付。** 在实施授权后的既有锁定环境中，先落地 F/G/M 的独立 fixture 与 oracle；这一步只增加验收支撑，不修改计量算法。记录源码／工作树摘要、依赖、镜像或宿主身份、策略、路径、工具可用性及每个结果的内容绑定。保留阶段 0 的冻结值和差异，不把有其他未提交工作的工作树简写为一个干净提交。

**执行边界。** 先执行适用的现有 CPU 回归与 F 组 CPU 槽位，记录未支持的提取、验证和计量状态。G/M 中针对未来功能的场景先保存独立 oracle 与 `not_implemented` 状态，不能把尚不存在的接口算作通过。R 组中需要 GPU 的真实 reference，以及真实 mapper 验收，单列为未运行项；没有相应执行授权与前置条件不运行。

**验收。** F 组 32 个路径槽位全部有明确状态；G/M 规格均有可独立计算的预期，R 组 16 个槽位保留身份与状态。现有 CPU 回归若失败，先判明环境、已存在问题和本任务引入的回归，不能隐藏。原始日志／JUnit、结构化结果和逐项摘要落在独立未提交结果目录。缺工具不等于算法失败；历史 B01/B02 不替代本次基线。

**退出边界。** CPU 基线完整后具备推进纯 CPU 阶段 1–3 实现的前置条件；缺少真实 mapper／GPU 结果仅阻止对应资格结论与正式晋级，不阻止无关算法开发。2026-10-20 宿主及项目 Python 缺少 `pydantic` 的问题，在 BASE-01 中通过复用固定依赖镜像解决，未修改宿主环境。前置条件满足不自动授权后续阶段；当前实施与回归缺口见 HANDSOFF。

## 3. 阶段 1：静态访问区域并集

### S1-01：定义结构化访问与底层存储身份

**归属。** `src/solar/ir/`、图形合同、operand provenance，以及对应 `tests/solar/`。复用现有 shape、dtype、输入绑定和 effects；不把 benchmark 的 workload 对象引入核心。

**工作。** 定义底层输入身份、base shape、静态索引映射、输出 slot、字节宽度、访问模式、可观察 effects 和精确性来源。两条 IR 路径分别从各自结构化语义生成这些信息；支持首批静态 unit-step slice、split、可证明的 transpose／reshape／view 组合。无法证明的 reshape、copy、动态索引及跨输入别名显式标记或拒绝，不从 display 字符串反推。

**验收。** F04/F07/F08 与 G04–G10 覆盖：同一 base 可追踪，不同 base 不误合并，多输出不串 slot，mutation 与 copy 不被当透明 view。坏元数据在进入计量前拒绝，合法未知访问保留原因。新增信息通过序列化往返；当前语义验证、alias、mutation 和适用的梯度检查不降级。

### S1-02：适配有预算的并集算法

**来源与范围。** 对照固定官方 master 的 `solar/analysis/access_regions.py`，记录移植函数、提交和许可，复用静态区域相交／划分思路。实现放在 SOLAR 分析层的单一职责模块，先搜索现有 helper，不引入重复工具层。

**工作。** 在 S1-01 的可证明坐标域内计算同一 base 的唯一元素并集；为矩形数、分解规模、时间等设置 canonical 上限。预算超限走有来源的保守下界或 unavailable，不能取可能高估必要读取的 bounding box。精确、保守、不可用结果分别携带原因；不把所有未知区域计成零再称精确。

**验收。** G01–G06 的元素数分别匹配独立枚举，尤其重叠为 96、带洞区域为 64、transpose 联合为 28；G07–G10 不产生不受证明支持的精确结果。小域参数化枚举验证重复不改变结果、交换访问顺序不改变结果、增加已证明访问不会减少并集。预算上限和拒绝分支可确定复现，不依赖 GPU。

### S1-03：接入读取计量并保留发布边界

**归属。** [graph_accounting](../../src/solar/analysis/graph_accounting.py)、分析结果合同和报告、[外层桥](../../src/sol_execbench/core/solar_bridge/)、相邻测试。

**工作。** 用已证明的 base 区域并集改进外部读取统计，保留逐 tensor dtype；输出物化、初始化、写入、effects 和内部容量流量继续分别处理。需要变更结果 schema 时原子更新读写双方；不得把“外部唯一读取更准确”写成“全部 cache-aware 流量已准确”。

**验收。** F01/F04/F05 的数学 oracle 精确一致；F07/F08 不错误取得纯静态／无 effect 资格。与 BASE-01 逐路径比较：不涉及区域改进的计量保持一致，变化项给出访问集合和差值依据；不以全局数值不变为目标掩盖修正。两条路径若有差异，保留原路径结果与原因，不择优取小值。

**阶段退出。** G 组全部符合其精确或拒绝预期，适用 F 组语义回归无新增失败，S1-01–03 的 CPU 检查完成。真实 R 组及正式资格是否完成单列；仅有 CPU 结果时仍不能声称已获得 GPU 或发布验收。

## 4. 阶段 2：受验证工件复用与三视图

### S2-01：分离固有计数、资源归属、硬件计价和证据

**归属。** [公共请求](../../src/solar/contracts.py)、分析层、artifacts、profile 及证据合同。官方 release 的 `scripts/reprice_execbench.py` 仅作为工作流参考，不能照搬其宽松重用条件。

**工作。** 设计从“已验证语义 IR”到“固有计数／访问集合”，再到“资源与精度归属、容量流量、速率计价”的分层。现有精度归属含 profile 依赖，不能简单缓存整个旧 analysis 并替换吞吐。定义完整身份、资格传播、逐阶段状态与下表失效规则；新接口不得允许未绑定的 YAML 绕过强制转换验证。

| 改变项 | 最少需要失效／重算的部分 |
| --- | --- |
| 源码、IR、shape、dtype、输入约束、effects、验证策略／语义执行身份 | 转换验证及所有依赖它的结果；执行身份采用明确字段，不能任意忽略环境变化 |
| 计数、访问区域或资源归属规则版本 | 受影响的计数／归属及下游计价；不能仅更改结果版本号 |
| 仅名义吞吐／带宽，资源模式、精度语义和容量不变 | 可复用绑定的语义及固有计数，重新计价；新情景重新判定资格 |
| profile 资源模式、精度支持或映射 | 重算归属与下游计价，必要时重算依赖它的计数／流量 |
| 缓存容量／层级、mapping 域、mapper 版本／配置／预算 | 容量证据重算，或从同身份且覆盖新容量的有效曲线选择；不得借用不覆盖该点的证据 |
| timeout／预算等行为输入 | 必须进入相应缓存身份；失败工件不得装作已完成结果复用 |
| 内容摘要、来源、文件清单或绑定损坏 | 拒绝加载，不静默再算后覆盖原工件 |

**验收。** M04/M05 的逐类变化有明确失效层级；保持语义的名义速率变化允许复用，资源／容量变化不会错误复用。schema、生产者、消费者、完整性检查和当前合同文档一起交付；未知／旧版本先拒绝再读业务字段。

### S2-02：实现受验证工件复用入口

**工作。** 复用现有内容摘要、验证证据和原子工件写入能力，新增受限的加载、检查与投影入口。工件明确绑定源与 IR、验证策略／结果、规则版本和派生关系；文件与身份检查在业务计算前完成。不导入可执行 Python/pickle 来恢复分析对象，不因为文件名或旧成功标志而信任内容。

**验收。** M04 的完整运行和复用结果在计数、流量、适用视图、时间和资格上等价，并用调用监测证明复用不执行 reference／重新取图。M05 的损坏、缺文件、旧 schema 和失效输入拒绝；M10 的半写入／中断工件不读为成功。缓存 key 包含所有行为输入，使用现有 canonical helper；重用成功不自动提升正式资格。

### S2-03：实现有明确假设的三个视图

**工作。** 按 A04–A07/A11 实现并分别报告：

- **unfused**：算子串行，逐算子取计算与 DRAM 最大值再求和；不宣称适用于跨算子并发。
- **ideal fused**：在列明融合／物化与理想存储假设下，按全图共享资源累加各模式耗时、独立资源取最大值，再与必要 I/O 项组合。
- **cache-aware**：复用当前支持的 Orojenesis 曲线、容量点和受限区域证据；仅对完整适用域返回完整视图，部分覆盖保留局部分析及 unavailable 原因。

保留目前正式下界的既有组合语义。新三视图先作为带假设的分析结果，不直接替换正式分数的 SOL 字段；不从官方三个同形字段复制公式。需要调整“全局 compulsory I/O + 最大额外量”时须另给不重复计数的证明和 oracle，不能直接求和。

**验收。** M01 得 16 与 10，M02 得 13；M03 容量单调性在相同合法域内成立，缺覆盖不能退回 ideal fused 再标成 cache-aware。输出逐视图记录模型、适用性、精确／保守来源、完整性和证据。fixture 与真实 mapper 验收分开；不存在无条件的三值排序断言。

### S2-04：接入公共 API、外层桥和对照报告

**工作。** 将 S2-02/S2-03 接入明确类型的公共请求／结果；由外层桥承担 workload 转换与批次组织，CLI 名称在实现时确定并配合同更新。保留显式 IR path，不创建静默 fallback。完整运行、复用分析和路径比较输出都能显示三视图及原因。

**验收。** 对 F 组和适用 R 组逐槽位展示 BASE-01／当前／复用结果，失败不删行。现有 API、外层 subprocess 边界、超时、发布拒绝与路径比较回归通过。假想 profile、部分容量证据、未知资格均不能继承旧正式 audit；两路径对照不得选更有利下界。

**阶段退出。** S2-01–04 及 M01–M05/M10 的 CPU／fixture 合同通过，当前正式发布路径无行为放宽。真实 mapper 的完整 cache-aware 能力和真实 GPU 接入另取对应证据；未运行时只交付已验收的分析子集。

## 5. 阶段 3：反向需求与敏感性探索

### S3-01：求模型下的必要资源需求

**工作。** 输入明确的目标时间、固定程序实例、分析视图、资源模型和容量；输出必要资源约束及不满足原因。首批支持固定容量的 ideal fused／完整 cache-aware 全图约束，以及指定资源组按共同倍率扩展的求解。独立资源分别列出需求，共用资源满足 `Σ_m W(r,m)/P(r,m) <= T_target`；未指定资源间交换关系时返回约束集合，不编造唯一硬件配置。

首批不支持的 unfused 反向求解明确返回 unsupported；不能套用全图公式冒充支持。若后来加入，必须针对 `Σ_v max(c(v), B(v)/BW) <= T_target` 单独求解和验收。改变容量的查询交给 S3-02 重算流量，不冻结旧 B 后直接外推。

**验收。** M06 得 60 ops/s、40 B/s，并由正向同模型复核；M07 共同资源倍数为 1.3。M08 所有无效时间／速率和缺资源场景拒绝。结果明确为必要条件，不把反代吻合写成设备可达性、产品推荐或性能保证。

### S3-02：实现有预算、可恢复的扫描

**归属。** SOLAR 核心负责架构情景及分析；外层负责 workload 枚举、并发和输出目录。复用 [resource_policy](../../src/sol_execbench/core/solar_bridge/resource_policy.py) 的预算思路，并核对 mapper 每作业线程数与总并发，避免只限制进程数。

**工作。** 首批扫描固定程序实例的吞吐、带宽和容量：速率点走受验证复用，容量点走覆盖检查／重算。预先固定参数网格、最大点数、总预算、每点超时和恢复规则；变化 shape 的每个实例必须重新提取和验证。恢复只认同身份完整工件，保留失败和中断，不改写旧目录。这里的扫描是分析工作，不隐含运行硬件性能实验。

**验收。** M09 恰有四个固定点，无遗漏／重复，名义资源改善不使相同模型下界变差。M10 分别覆盖容量失效、缺 mapper、超时、总预算、进程清理、恢复漂移和部分成功，所有计划点都有状态。测试情景使用独立身份，带旧 audit 的假想 profile 也没有正式资格；无需真实 GPU 完成控制流验收。

### S3-03：报告、回归与阶段交付

**工作。** 输出参数—约束—下界对照、瓶颈／敏感性和目标可行的必要条件。保留同程序、同路径、同视图的基线点；如果输出 Pareto 集，必须预先定义可比较的多目标及单位，无成本／面积／功耗模型时不声称找到了最优芯片或商业性价比。并列点采用稳定规则，缺失点保持可见。

**验收。** F/R 分母与阶段 0 一致，新增参数点另列分母；报告区分语义通过、计量可用、完整容量覆盖和正式资格。M06–M10 通过对应 CPU 合同，抽样点与独立正向公式一致，恢复运行与未中断运行按身份得到相同完整点结果。未运行真实工具／设备的部分明确标出，无新的加速或硬件达标结论。

**阶段退出。** 反向查询支持域、扫描预算与所有失败路径已记录；对外 API／CLI／文档一致，三视图与原正式发布字段的关系清楚。需要正式晋级时另安排限定的真实 mapper／设备资格任务，按当时现有资格链与设备身份执行；阶段 1–3 的 CPU 完成不自动关闭该项。

## 6. 每个实现任务的共同完成条件

1. 交付范围、复用来源、支持／不支持域及影响的样本 ID 可审查；不改变失败分母和默认验证强度来取得通过。
2. 新行为的独立 oracle 与现有相关回归通过；Python 变更完成相应 Ruff、ty、coupling、readability 及 Pytest 检查。先跑相关范围，只在新风险需要时扩大；不得使用 `-n auto`，CPU 基线可显式串行，GPU 用例保持独立。
3. 需要 schema 变化时完整更新 canonical registry、producer、reader、fixtures、CLI 合同和文档，不保留兼容旧版本分支。
