# 算子版本升级性能退化 Agent 回测方案

日期：2026-10-11。目标是用已有退化调查，判断 TritonBench/TritonParse、FlyDSL skill 和 agent-sh/perf 能直接承担哪些工作，以及剩余工作值得做成集成层还是独立产品。本方案不启动安装、构建或 GPU 实验。

先复用已有证据做受限回放，找出工具能力与输入要求的差异；再让最有希望的两套方案在相同 GPU 条件下重新调查。不要先开发完整 Agent 再用已知答案证明它有效。

## 一 回测能回答什么

分开回答三个问题，分别报告结果，不合成一个排行榜：

1. **工具复用价值。** 给足文档要求的输入后，能否完成测量、二分、恢复与证据保存？
2. **自主调查能力。** 只给升级信息和初始退化，Agent 能否自己选测量对象、组件与实验，逐步缩小原因？
3. **独立开发价值。** 普通 coding agent 加现成工具仍做不好的步骤，是否反复出现，而且值得用专门实现解决？

当前 AMD 案例是一场升级事件，下面的任务只是它的不同检查点，不能算作多个独立事故。历史回测用于开发决策；证明跨厂商泛化还需要未参与设计的案例。

## 三 从同一案例拆出四个任务和两个控制任务

表中的期望结论只供评审者使用。独立任务用于定位能力缺口，不能串联前一任务的答案给下一任务后，再声称完成自主发现。

| 任务 | Agent 初始得到什么 | 要检验的能力 | 接受结论及禁止越界 |
| --- | --- | --- | --- |
| T1 主机与设备时间分离 | G1 FP16 GEMM，M=359、N=211、K=127；旧新环境及普通调用退化，冻结输入和原始调用入口 | 选择 graph、连续主机提交、生成 runner、CPU profile 等对照，找到配置 hook | 保持配置语义、把重复设置恢复移出循环可解释主要提交差距；调用跟踪支持重复状态维护。不能说热路径重建了哈希/字典，不能把 event 残差全部归给 Python 3.14 |
| T2 库与 runtime 分离 | C1 FP32 `A @ (B+B)`，M=16、N=16、K=32；旧新环境和初始退化 | 缩减原生 GEMM；在兼容条件下交叉换库/runtime，查实际装载，再枚举合法算法 | 退化主要随 hipBLASLt bundle 及算法资源变化；更换候选能改善但不足以恢复。不能把 bundle 当一个 `.so`，不能把 rank 当稳定算法身份 |
| T3 两个因素的交互 | 明示前置条件已完成：同 tile、固定新版内核仍慢；给两侧二进制、元数据和复现入口，不给分支补丁或四组表 | 从代码和 profile 提出因素，设计完整四格干预及 A/A，解释条件效果 | 尾处理与标量写回存在交互；计数和反汇编支持额外 LDS 地址计算。不能简单相加收益，不能把约 0.682 μs 全分给 97 条 VALU，不能称与旧版性能等价 |
| T4 行为到提交的溯源 | 明示已发现的配置维护与写回行为；实际构建身份、源码仓库和版本范围，不给五个 SHA | 追踪历史、校验祖先/发布分支关系、回放局部行为，判断二分是否适用 | 能关联相关 diff 并说明证据等级即得相应分；没有完整父子重建就不能宣称提交净影响。允许多提交候选及非线性历史，无需强迫输出唯一 culprit |
| C1 原始重复对照 | 同版本 A/A 的盲化测量，另给 G2 波动样本 | 拒绝把噪声解释为确定的升级原因 | A/A 无证据支持版本退化；G2 保留不确定，允许请求更多样本。不能因为没有显著差异就宣称严格等价 |
| C2 环境失败 | 新 Torch 加载旧 hipBLASLt 的实际缺符号日志和环境清单 | 分清 ABI/构建失败、错误输出与性能结果，提出可执行替代实验 | 将失败标为不可测，转向独立 native 客户端或明确停止。不能把失败变成极慢样本、零耗时或坏 commit |

评审可参考历史量级，但不要求新测量复现小数点：T1 主机提交约 16.55→18.40 μs，配置外移后约 15.86/15.83 μs；T2 的库/runtime 四格约 4.02–4.07 对 8.84–8.89 μs；T3 的四条路径约 6.581、5.046、5.349、4.489 μs。这些是既有实验，不是未来验收阈值。

T3 是“给定同 tile 定位之后”的条件任务；T4 是“给定行为之后”的条件任务。只有后续从初始升级告警独立开始的完整调查，才能评价端到端能力。

## 四 固定被测工具和比较组

以本次已核验快照开始，避免回测期间工具变化。运行前补齐依赖 lock、镜像摘要、license 与模型配置。许可证核查决定能否分发或直接嵌入，功能可复用不自动等于可以不附条件地复制代码。

| 比较组 | 固定版本与角色 | 公平比较条件 |
| --- | --- | --- |
| G 普通 Agent | 与其他组相同模型、推理设置和工具权限；只有通用调查目标 | 作为基线，检验专门流程是否真的增加价值 |
| T Triton 工具组 | TritonBench `dabe5714d2cfa76ad1ee8a3237ee730b4a5a8627`；TritonParse `219a2e124f8b80e942f20123f7d7103e765dea39` | 同一个普通 Agent 调用公开工具；不得把未公开 AI diff 模块算作可用能力。gfx1200 runner 和 hipBLASLt 支持要核验，不能从 H100/MI350 workflow 推断 |
| F FlyDSL skill 组 | FlyDSL `43ec5da9d934057b60f06d32ff05a8e044f9020c` 的 `bisect-perf-regression` | 同模型执行固定 skill。其要求的 good/bad 和 bench command 作为显式输入契约，不暗中替它选对目标仓库 |
| P perf 调查组 | agent-sh/perf `7d1ffea9ec9c7ef5f0ed578b5daf777c022dcd0e` | 同模型使用实际阶段 runner。指标格式转换单独记录；不得把负载参数二分称为 commit bisect |
| C 现有工具组合 | 同模型可用上述三套公开能力，自主选择 | 检验“集成现成工具”能否已满足需求。协调提示只说明任务和工具，不给诊断顺序、因素名称或答案 |

来源：[TritonBench workflow](https://github.com/meta-pytorch/tritonbench/blob/dabe5714d2cfa76ad1ee8a3237ee730b4a5a8627/.github/workflows/bisect.yaml)、[TritonParse 二分契约](https://github.com/meta-pytorch/tritonparse/blob/219a2e124f8b80e942f20123f7d7103e765dea39/tritonparse/bisect/README.md)、[FlyDSL skill](https://github.com/ROCm/FlyDSL/blob/43ec5da9d934057b60f06d32ff05a8e044f9020c/.claude/skills/bisect-perf-regression/SKILL.md)、[perf README](https://github.com/agent-sh/perf/blob/7d1ffea9ec9c7ef5f0ed578b5daf777c022dcd0e/README.md)。

每组分两种适配等级，结果分栏：

- **原有能力验证：** 保持上游正常入口与必需参数。只测试其声明支持的步骤。不适用写“不适用”，不要伪装成归因失败。例如缺少可运行父子构建时，不能拿一个没有测量谓词的 hipBLASLt 任务评价 TritonParse 二分准确率。
- **统一接口调查：** 五组使用同样的测量、源码读取和实验请求接口。只转换参数、单位、指标输出和退出码；每处兼容修改有 diff 和人工工时。新增组件规划、因素选择、二分目标选择不能藏在适配器里，那已经是待评估的新能力。

perf 的默认 60 秒采样、资源约束阶段和 FlyDSL 的三次中位数都属于被测流程。原有能力验证按各自规则计成本；统一接口组只使用统一测量协议，并显式标注配置覆盖。给 CPU 提交任务施加额外 CPU/内存限制会改变实验，应独立标记为干预，不能混进基线。

## 五 防止答案泄漏

所有受测 Agent 必须从无本对话历史的新会话开始。当前对话已经包含完整答案，不能直接用当前上下文跑“盲测”。

准备三个互相隔离的区域：输入包只含最初告警、冻结输入、原始工作负载、端点环境和允许的源码；执行区域保存 Agent 自己的实验及日志；答案区域保存报告、历史干预、评分规则和标签映射。受测进程不能访问后者，也不能挂载整个当前工作目录或 Codex 历史。

原始目录名、脚本名、缓存路径和注释可能含 `epilogue`、`vector-only`、`config-hook` 等答案。封装人员逐项审查并给材料中立 ID；保留必要的版本和二进制身份，私有映射记录哈希。不能仅改文件名却暴露脚本中的解释。预写好的干预补丁不进入初始包。

允许访问固定版本源码和普通 commit diff，这本来就是调查能力；禁止读取本案例事后报告、修复说明和含最终答案的 issue。网络由代理或快照白名单执行，不能只靠提示词。所有越界请求及实际读取记录留存。公开源码仍可能被模型预训练见过，因此历史任务称开发回放，不能作为严格无污染测试。

被测工具内部需要的子 Agent 也受同一数据边界约束。正常请求缺少信息时，评审只返回预先定义的事实；人工提供原因、选定因素或替写补丁后，剩余结果标为辅助完成，不计自主完成。

## 六 先回放证据 再运行完整调查

### 阶段一 封装和契约验证

预计 1–2 人日，GPU 预算为零。核对归档引用，准备六个隔离任务包、私有评分清单及三套工具的最小调用说明。离线检查输出能否完整表达单位、指标对象、样本身份、正确性、失败和恢复状态。

退出条件是：答案隔离经人工复查；各任务能够追溯到原始数据；明确哪些脚本可作为原始复现入口、哪些是已经带答案的诊断程序；每套工具有“可用、不适用或缺少前置条件”的列表。不要为了做一份格式适配先搭完整服务。

### 阶段二 受限证据回放

先做五组 × 六任务 × 一次，共 30 次。每次上限 30 分钟、60,000 个总输入输出 token，子 Agent 用量合并计入；这是建议预算，需要记录具体模型及价格后估算费用。最多 30 个不同实验请求、最多一次纯环境重试，不因看到结果不理想临时加预算。

Agent 提交实验请求，证据提供器只返回归档中与请求条件完全匹配的原始数据。请求必须写清所变因素、固定条件、测量对象和预期可区分的假说；条件不匹配返回“历史材料不存在”，不能插值、编造中间 commit 耗时或借用邻近 shape。

这个提供器是回放装置，不是实际 shell/GPU 工具。它只评价“下一步问得对不对、能否正确解释证据”，不评价构建成功率、二分执行可靠性或自主补丁能力。上游 runner 在此阶段不能执行的部分记为未测，不能拿回放结果包装成原生工具成功率。

问题不在回放表中时，Agent 可以提交有效的新实验设计。评审记录其可区分性和成本，保留待执行；不因此自动判机制已确认。提供器能够回答哪些条件本身会限制搜索空间，应在结果中披露。

按各任务达到的证据等级及错误归因选两组进入重复回放；若接近，优先保留 C 组合组及另一个成本最低组，不根据单个漂亮回答选冠军。两组在四个正向任务各增加两个独立会话，共 16 次；合计 46 次回放上限 23 Agent 小时、276 万 token。它只检验本事件内的流程稳定性，不估计跨事故成功率。

### 阶段三 少量真实 GPU 调查

仅在材料、原有能力和回放结果都明确后启动。两套入选方案各做两次独立调查，共四次；每次从 T1/T2 之前的原始升级告警开始，允许自行发现两条路径、提出干预并停止于证据边界。不能把 T3/T4 的前置答案一并给它。

每次最多 120 分钟总时间、60 分钟目标 GPU 租约占用、120,000 token、20 个不同实验设计。每个设计的重复次数由测量协议决定，不允许把一次采样拆成多个“实验”。总上限 4 GPU 小时、8 调查小时；调试和失败租约也记账。预制镜像及编译缓存等共同准备成本另记，一次构建工时不能藏进零成本工具调用。

四次调查冷启动 Agent 状态；各组从同一缓存快照开始，运行顺序交替。调查结果不得跨组共享。恢复超时、正确性失败或硬件身份错误立即停止该实验；恢复无法确认时停止本机后续 GPU 任务，保留现场，不能为了跑完比较继续采样。

完整 PyTorch/hipBLASLt 历史构建另设阶段，不占用“现有镜像调查”名义隐性加时。先批准具体父子对和兼容构建配方，再分配预算；没有完成时，T4 的提交净影响继续为未验证。构建兼容补丁必须共同适用或形成独立因素，不能一侧修补后把所有差异归给目标提交。

### 阶段四 判定是否值得增加专门实现

先输出每一步的失败类型，再做最小增量实验。例如只增加“库/runtime 组合规划”，或只增加“交互实验选择”，不要同时换模型、提示、执行器和评分规则。用相同输入、模型和预算与 C 组合组比较；改善后在新案例上复核。

NVIDIA 扩展优先选 [PyTorch #114911](https://github.com/pytorch/pytorch/issues/114911) 的库版本/分派回归，但必须先独立复现，原 issue 数字不能作为本地结果。[CUTLASS #3463](https://github.com/NVIDIA/cutlass/issues/3463) 与 [#3389](https://github.com/NVIDIA/cutlass/issues/3389) 可补代码生成和交互任务；其公开缩减材料只编译，不能计作运行性能归因成功。硬件与旧包可用性是这些任务的准入条件。[已有案例边界](nvidia-library-regression-research.md)

## 七 所有真实测量共用一套有效性规则

1. AMD 目标机器复用现有排他 GPU 锁、UUID/BDF 核验、ClockLease/host guard 与共享命令契约。两侧都要求已核验 STABLE_PEAK；设置失败不采样。最外层拥有者负责结束及异常后的 AUTO 恢复核验，借用者不能提前恢复外部持有者。AUTO 无性能样本用途。外部失效需要恢复流程处理，不能承诺任意 SIGKILL 或断电都能由 finally 自动恢复。
2. 冻结输入、候选源码、图捕获/缓存策略、预热、CPU 亲和性、镜像与实际加载二进制；移植 native 问题时核对 M/N 转置和完整数值检查。计时前后检查正确性。
3. 主机提交、单调用 event、graph 平均时间是三个指标；不可相加，也不可用后者直接替代端到端延迟。统一输出耗时比 `candidate/baseline`，大于一表示变慢；已有 `paired_analysis.py` 使用相反方向，且限定 24 workloads × 10 blocks，不能直接套在本回测。
4. profiler 与计时分开运行、单独计预算。计数按版本内算法 ID、真实 kernel 和 dispatch 绑定；不能跨 wave size 当 FLOP 比较，不能将零 PMC 自动解释为未执行。
5. 确认某个两臂或四臂实验，预注册六个独立进程配对区块，区块内顺序平衡，使用进程内中位数。A/A 在相同协议下采集六个区块并在候选测试前冻结阈值。建议两臂差异门槛为 `max(基线耗时的 5%, 同指标 A/A 最大绝对配对差的 2 倍)`；交互项另用四臂同条件对照确定噪声，不借用两臂噪声。
6. 首轮统一将超过门槛且六个区块方向一致的差异标为“在本协议下重复支持”；未满足则不可判定，不追加采样追求过线。该门槛是工程筛查，不能称统计显著性或普遍等价证明。输出所有区块和效果量，正式外部结论需要单独预注册统计设计。

复用入口：[时钟租约](../../src/sol_execbench/core/bench/clock_lock.py)、[所有权与借用](../../src/sol_execbench/core/bench/clock_ownership.py)、[host guard](../../src/sol_execbench/core/bench/host_clock_guard.py)、[设备及失败策略选项](../../src/sol_execbench/core/bench/rocm_profiler/pmc_clock.py)、[命令契约](../../src/sol_execbench/core/platform/clock_commands.py)。这些现有能力需要在回测入口验证接线，不能重新写另一套 sudo/恢复脚本。

## 八 评分按证据节点记录

每次报告给出下列向量，而不是只给一个“根因正确率”。每项用“未达到、部分、达到、不适用”，并列原始证据 ID：

| 维度 | 达到的条件 |
| --- | --- |
| 测量有效 | 明确测量对象，满足时钟/正确性/输入/样本规则，profiling 时间不充当性能 |
| 责任层定位 | 用对照排除或保留 CPU、框架、库、runtime 路径，而非只根据热点命名 |
| 行为溯源 | diff 与实际构建行为相符；区分源提交、二进制变化和完整提交效果 |
| 干预验证 | 实际执行针对假说的改变，验证预测与输出；只有设计或读历史结果属于部分 |
| 交互识别 | 有完整四格、配对效果与机制证据，未把条件收益错误相加 |
| 边界准确 | 保留残差、不兼容和证据缺失；C1/C2 不伪造确定根因 |
| 工程成本 | GPU 租约/执行时间、构建时间、token、请求数、人工分钟、适配 diff 和失败次数完整 |

每条原因结论至少包含：作用对象、条件、假说、干预、结果、证据 ID、已排除项、仍未知项。评审先用确定性核查对照数据和引用，再由不知道组别的评审者判断因果措辞；争议保留双评审说明，不让同一个 Agent 自己给自己打分。

严重错误单列：错误输出仍当有效性能、环境失败当退化、无执行记录却宣称完成干预、profiling 时间进入性能结论、把未重建提交的净影响说成已证明。出现时该条因果链不验收；其他已完成节点仍保留，不用总分掩盖或抹除。

## 九 复用与独立开发的决策表

“复用候选”表示已有实现或本库已有机制；仍需接口和运行验证。“缺口候选”必须在回测中暴露，不能预先算作我们的优势。

| 环节 | 优先处理 | 什么结果才支持另做实现 |
| --- | --- | --- |
| 算子 benchmark 组织与回归检查 | 复用本库冻结输入/执行能力及 TritonBench 模式；做薄适配 | 上游和本库都不能表达必要测量对象，而非仅 JSON 字段不同 |
| 单仓库二分与 Triton→LLVM 追溯 | 复用 TritonParse；用 FlyDSL 验证交互式 SOP | 遇到真实多仓库非线性历史及兼容性问题，现有能力无法保持有效比较 |
| 假说、单变量实验和证据日志 | 优先复用 perf 的阶段执行器/流程 | 在相同工具和预算下仍反复选无信息实验，而结构化实验选择能稳定改善 |
| GPU 锁频、独占、恢复、数据身份 | 复用本库现有机制 | 这是执行底座，不应拿来当新的 Agent 创新点 |
| 多组件组合与 ABI 约束 | 先用普通 Agent 加工具组合测试 | 无法自动构造有效库/runtime/编译器替换；需要显式版本依赖图和构建计划 |
| 多因素条件效应与交互 | 先测试 perf/组合组能否自行补足四格 | 长期停在单因素解释，遗漏交互；新增规划模块可降低错误归因或实验成本 |
| 源码到实际库、算法、ISA 的绑定 | 复用现有证据后测试自动化 | 新工具反复分析错二进制/算法，需要统一身份绑定与可追溯证据连接 |
| 不可判定与结论强度检查 | 先用明确报告契约 | Agent 反复把猜测写成事实，确定性规则能阻止这些越界且不抹除有效结论 |
| 新版本监听和告警 | 后续接 CI/webhook | 不是本轮差异重点；不用先建常驻监控服务来掩盖归因能力未验证 |

## 十 本轮结束后如何决定投入

- **以集成为主：** C 组合组在 T1/T2 上稳定定位并验证，在 T3 上能补齐交互，在 T4 上守住提交效果边界，两个控制任务无严重误判；剩余成本主要是输入和命令适配。做集成、文档和上游贡献，不先开发新的推理框架。
- **做小型专门模块：** 同一个缺口在两组和重复会话中出现；一次只补一个模块后，在相同预算下达到更高证据等级，或以更少 GPU/人工成本达到同等级。对当前单一升级事件只能称原型证据。
- **独立立项：** 上述增量在至少三个独立升级事件上重复出现，覆盖两个厂商或两种软件栈，其中至少一个未参与模块设计；错误归因没有增加，并且实际使用者愿意投入集成。这个标准是建议的内部立项门槛，不是统计泛化证明。
- **停止或缩小范围：** 历史镜像/输入不可恢复、公开材料仅编译却被要求运行、干预正确性不能保证，或搭建成本远大于调查节省。将不可测项从适用范围中明确排除，不把它们填成成功或普通失败。

下一步可执行交付是六个隔离任务包、私有评分依据、三套工具的薄适配清单和阶段二预算表。完成这些后才有条件启动回放；GPU 调查及新模块开发属于后续执行阶段。
